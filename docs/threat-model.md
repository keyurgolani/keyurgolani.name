# Threat model

This lists what the platform protects, from whom, where an attack comes in, what stops it, which issue owns that control, and the test that proves it.

A row is `in place` when its control has merged and every test it names exists. A `planned` row names the test its owning issue will add, by the title it will have. `pnpm test` checks the tables (`ci/threat-model.test.mjs`): every section below holds one table with exactly these columns and at least one row, every row names a test and its status matches its tests, and each test cited by file is a test that runs under that title, never a comment, an assertion message, or a skipped test.

## Scope

The app runs from one image under one of three profiles (see [deployment](deployment.md#profiles)):

- `owner` serves the real portfolio and, with #2, an authenticated Studio backed by a writable data directory.
- `read-only` serves a mounted source. It has no Studio and never writes.
- `demo` serves a bundled sample and a public sandbox Studio whose state stays in each visitor's browser. It has no owner services.

The rows defend against:

- Anonymous visitors: anyone who can reach the site or the app port.
- Cross-site pages: another site open in the owner's browser.
- Same-site pages: script on a sibling origin, such as a demo at `demo.<owner domain>`. Browsers count a sibling as the same site, so `SameSite` cookies go along with its requests to the owner origin.
- Content: the owner's documents, files imported into the demo, and data fetched from GitHub. Content is treated as untrusted markup wherever it renders.

The operator, who runs the container and holds its secrets, is trusted. Out of scope: a compromised host or operator, the TLS proxy's own security, floods beyond the limits below, and more than one user (there is one owner and no roles).

One risk is accepted rather than closed: sign-in can be held off (login-8). With no trusted proxy hop, sign-in has only its global limits, so one client that keeps both verification slots busy, or all 16 places to wait out the slowdown taken, gets the owner's own sign-in a 429. Running behind a proxy with `PORTFOLIO_TRUSTED_PROXY_HOPS` set gives each source its own limit, one of those places, and one verification slot at most, but many sources, such as rotating IPv6 /64s, can still keep the room full. Being turned away never counts as a failure, so it never gets the owner's own source blocked, and the owner gets in by retrying once a place frees.

## Assets

| Asset           | What it is                                                                  |
| --------------- | --------------------------------------------------------------------------- |
| Credential      | The owner password and its scrypt hash                                      |
| Session         | Session tokens, CSRF tokens, and the cookie that carries them               |
| Drafts          | Unpublished content, revision history, and owner settings                   |
| Private content | Records marked private, and location and camera metadata in media           |
| Live site       | What visitors see, and the pointer to the live revision                     |
| Identity        | Who the site says it belongs to, in metadata and search results             |
| Configuration   | Deployment settings, secrets, and server paths                              |
| Data directory  | Sessions, audit records, and revisions on disk                              |
| Demo state      | What a demo visitor imports or changes, kept in their browser               |
| Visitors        | People browsing any profile, and their browsers                             |
| Audit trail     | The record of sign-ins, revocations, denials, publishes, and rollbacks      |
| Server log      | What the server writes to stdout and stderr, which operators read to run it |
| Availability    | The server's CPU, memory, and disk                                          |
| Repository      | CI secrets, the published image, and what goes into it                      |

## Updating this file

A change that adds an entry point, an asset, or a control adds a row to its area with the next free ID, or edits the row it changes. When a planned test lands, cite it by file and title instead, and set the row to `in place` once nothing in it is planned. The threat tables skip Prettier's column alignment, so a change to one row stays a one-line diff.
