# Building a variant

A variant is a composition: a workspace package that decides how the portfolio's sections are arranged, how a visitor moves between them, and what reveals itself. The host renders it from one `VariantRenderInput`, built by `buildRenderInput` in `@portfolio/variant-contract`: the visible content (no hidden section, no unregistered extension data), the site's presentation settings, the variant's control values, the route, ids, and a fixed time and seed.

Appearance values aren't a variant's. Color values, font families, materials, focus and state colors, and motion timing come from the appearance system (#19), whose design languages, color schemes, and typography packs the owner picks independently. The variant designs its own components and elements from those values: which of the language's radius, border, and shadow tokens each part takes, the type step it's set in, the role surfaces it sits on, and its own geometry. A variant ships no palette, font, theme, or theme toggle.

For an AI-assisted variant build, point an agent at [skills/variant-developer/SKILL.md](../skills/variant-developer/SKILL.md).

## Anatomy of a variant

```
packages/variant-<id>/
├── package.json     @portfolio/variant-<id>, with "portfolio": { "kind": "variant", "manifest": "./manifest.json" }
├── manifest.json    contract 2.0 or 2.1: id, promise, composition family, kinds, routes, controls
├── tsconfig.json
├── DESIGN.md        the design contract, from the skill's template
└── src/
    ├── index.tsx    the default export: ({ input }) => the page
    ├── styles.css   layout and element design from the tokens, every selector under [data-variant='<id>']
    └── renderers/   one bespoke renderer per kind in renderedKinds
```

`package.json` exports `.` (the component), `./styles.css`, `./manifest`, and `./package.json`, plus a subpath per enhancement. It may also export `./studio-thumbnail`, the pure drawing Studio's composition picker and Compare's grid show for it, which default-exports a `StudioThumbnail` from `@portfolio/kit/studio-thumbnail`; registry generation maps it by id into `src/lib/generated/registry.thumbnails.ts`, and a variant without it gets Studio's generic plate. Every first-party composition in `COMPOSITION_IDS` ships one in `src/studio-thumbnail.tsx` (`packages/variant-contract/src/node/thumbnails.test.ts` fails naming any that doesn't), and `pnpm new-variant` scaffolds a starter.

## Quick scaffold

```sh
pnpm new-variant my-id
```

It copies `packages/fallback-composition` to `packages/variant-my-id`, with the two stills its manifest lists, names the package and the manifest, adds it to `@portfolio/web` with `pnpm --filter @portfolio/web add @portfolio/variant-my-id@workspace:*`, and runs `pnpm check:variants --package @portfolio/variant-my-id`. `--no-install` stops before the two pnpm commands. The stills show the fallback's render, which the scaffold's is; `pnpm stills --variant my-id` shoots the variant's own once it looks like itself.

### A first-party composition

A composition of the platform's own goes further: its id is reserved and its tier and motion pinned, and a dozen lists name every composition. One command does all of it:

```sh
pnpm register-variant swiss-signal --family document --motion subtle --tier light \
  --css 9216 --js 1024 --enhancement 4096 --animation 0 \
  --promise "The portfolio as a Swiss print poster that works as an index." \
  --description "A 12-column ruled grid: the thesis as a poster, the work as a ruled index, and every collection a ruled table."
```

It scaffolds `packages/variant-<id>` as `pnpm new-variant` does if it's missing, with the family, motion, tier, budgets, promise, and description given (`--image` defaults to 61,440 bytes for the stills, `--font` to 0, and `--name` to the id in title case). The promise and description are required, so the manifest carries the composition's own copy from its DESIGN.md, never the scaffold's "Replace this with..." placeholder, which `pnpm check:variants` refuses in either field. Then it adds the id to `COMPOSITION_IDS` and `FIRST_PARTY_PINS` in `packages/variant-contract/src/ids.ts`, to `COMPOSITION_STATUS` in `packages/variant-contract/src/status.ts` as `pending`, the workspace dependency in `apps/web/package.json`, a seed weight in `ci/shard-durations.json`, the composition lists in `tests/quality/{cells,checklist}.test.ts` and `apps/web/scripts/variant-css-budgets.test.ts`, the "this build registers" messages in `apps/web/scripts/config.test.mjs` and `skills/portfolio-author/scripts/validate.test.mjs`, and the lists in `docs/configuration.md`, this page's first-party compositions, and the variant-developer skill. It writes `quality/units/<id>.ts`, with `distinct: 'pending'` and `coverage: 'pending'`, and the VoiceOver with Safari template in `quality/manual-runs/templates/`. Last it resolves the lockfile offline (`--prefer-offline` only when the cache lacks a package or its metadata), and puts it back and stops if anything changed besides the new package's link and importer, such as drift from another edit in the tree; then it links the package with a frozen install, and runs Prettier over what it touched and `pnpm check:variants --package @portfolio/variant-<id>`. `--no-install` stops before them. The composition lists in the space and type lint tests come from `COMPOSITION_IDS`, so it never edits them.

It works out every edit before it writes one, so a list it can no longer find stops it with nothing changed. A second run changes nothing, and two runs on the same tree write the same bytes. It leaves an existing package and entry as they are, and refuses arguments that disagree with them, naming each field: the family, motion, tier, `--name` when given, and every budget, against the manifest. It also refuses an id that isn't a registry id, `fallback`, `missing-variant`, a quality surface's id, the reference variant's, and another package's, and a `--name` over 60 characters, on more than one line, or with `<`, `>`, `*`, or a backtick. `tests/variants/distinct.json` isn't one of its files: its thresholds and controls are measurements, which `PORTFOLIO_DISTINCT_CALIBRATE=1` takes again once a design lands.

A pending composition registers, renders, and runs every suite, but an owner can't reach it yet: `/sample?variant=<id>` renders the sample's own composition in its place, at the canonical URL, a recipe that selects it isn't offered, and Studio's picker lists it disabled, labelled "In progress", with no thumbnail (`status` and `statusLabel` on its catalog option). Its lane sets it to `ready` in the merge whose home and case page have both passed design review, since an owner opens the case page from the picker too. The variant specs check it on the sample all the same: their server sets `SAMPLE_PENDING_TEST_OPT_IN=1`, which nothing else sets.

Register one scaffold at a time. Two compositions that are both still the fallback's copy render the same page, and the distinct guard's pixel check fails any such pair, pending or not, so a composition's home slice lands before the next one registers. Its lane also brings its paragraph in `docs/architecture.md` up to date at P1, which the script doesn't write.

## Registration

Installing a variant is a dependency of `@portfolio/web` and nothing else. `apps/web/scripts/build-registry.ts` reads the host's direct dependencies and keeps those whose `package.json` `portfolio.kind` is `variant` or `content-extension`, or one of #19's pack kinds, `design-language`, `color-scheme`, and `typography`. It checks each, and writes the gitignored `apps/web/src/lib/generated/`: `registry.meta.ts` (the manifests, the packs with their compiled files, and `ASSET_MANIFEST`, what each unit ships to the browser), which is `server-only`, so no client module can bundle it; `asset-manifest.json` and `trace-matrix.json`, which Node tools read in its place; `registry.loaders.ts`; `registry.extensions.ts` (the content extensions' definitions, which Node tools load); `registry.renderers.ts` (their section renderers, which only the server loads); `registry.enhancements.ts`; `registry.thumbnails.ts` (each variant's `./studio-thumbnail` drawing, by id, which Studio's picker imports); and `transpile-packages.json`, which `next.config.ts` reads. The packs' compiled stylesheets go into the gitignored `apps/web/public/_portfolio/pack/`, the fonts they ship into `apps/web/public/_portfolio/font/`, each variant's compiled stylesheet into `apps/web/public/_portfolio/variant/`, and the images it names into `apps/web/public/_portfolio/asset/`. It writes each variant's experience segment too, `apps/web/src/app/(site)/%5Fexperience/<id>/`: the route its pages render in, which imports that variant and no other, so a page's chunks hold no other variant's code. Two runs on the same dependencies write identical files.

Your stylesheet compiles into one file, `<id>.<sha256-12>.css`: #19's layer-order statement, then the kit's shared renderers' layout (about 3 KB gzip, which counts against your `css` budget) and your `./styles.css`, with your own `@import`s inlined, all inside the `variant-layout` cascade layer, so a rule of yours for the same element still beats the kit's. Each `url()` target in your package, an image, is copied by content hash to `/_portfolio/asset/<sha256-12>.<ext>` and the `url()` rewritten. The host links the file only on a page that renders your variant. Declare `"sideEffects": false` in your `package.json`, as the scaffold's does: nothing in a variant runs on import, and a bundle then keeps only the modules a page uses.

`predev`, `prebuild`, `typecheck`, `test`, and `check:variants` run it, and any error stops them; `typecheck`, `test`, and `check:variants` pass `--modules-only`, which writes the modules and the experience segments and leaves `public/` alone. Under `next dev`, an edit to your stylesheet reaches the page once registry generation runs again: run `pnpm --filter @portfolio/web build:registry`, or restart `pnpm dev`. Installing never runs it, so a broken package can't block `pnpm --filter @portfolio/web remove <package>`. Run it yourself with `pnpm --filter @portfolio/web build:registry`, `--check` to write nothing, and `--format json` for the whole result.

It refuses a package with an invalid manifest, a contract major it doesn't read or a newer minor, a token contract or schema range this host doesn't match, a reserved or duplicate id, a reserved route segment, or a missing export or file. Each diagnostic names the package, its version, the manifest path, a JSON pointer, the code, what it expected and found, and the remedy: upgrade, pin, or uninstall. Without the fallback composition among the dependencies, generation fails.

A `file:` dependency must sit under `apps/` or `packages/`, the trees the Docker image's dependency stage copies.

## The manifest

`manifest.json` at the package root. The fallback composition's is the smallest correct one:

```json
{
  "id": "fallback",
  "name": "Fallback composition",
  "promise": "Every section in content order, in one readable column.",
  "description": "The host's stand-in. ...",
  "contract": "2.0",
  "schemas": { "portfolio": { "min": 3, "max": 3 }, "site": { "min": 2, "max": 2 } },
  "tokenContract": 1,
  "compositionFamily": "document",
  "motionIntent": "still",
  "performanceTier": "light",
  "budgets": { "js": 2048, "css": 2048, "image": 0, "font": 0, "animation": 0, "enhancement": 0 },
  "renderedKinds": [],
  "unsupportedKinds": [],
  "contentSlots": [],
  "routes": { "home": "shared", "work": "shared", "views": [] },
  "controls": { "version": 1, "items": [], "migrations": [] },
  "visitorControl": { "placement": "header" },
  "textDirection": ["ltr", "rtl"],
  "provenance": { "provisional": true, "sources": [] }
}
```

`renderedKinds` are the kinds the variant renders bespoke, `unsupportedKinds` the ones it deliberately doesn't show, and every other kind renders through the kit's shared renderer. A composition whose `renderedKinds` and `unsupportedKinds` hold every core kind between them may set `"kitLayout": false` (contract 2.1): its stylesheet then compiles without the kit's shared layout, so its own `pf-` parts, if it places any, and an extension kind's shared section get none of it. `renderSection` throws if it passes a kind back to the kit's own renderer, whose markup would show unstyled, and registry generation warns (`registry.kit-layout-extension`) for each installed extension kind it neither renders nor declines. Controls are owner-tunable composition choices, never appearance. `budgets` is what the variant may ship, in JS, CSS, image, font, animation, and enhancement bytes or counts, each at most its tier's ceiling in `runtime-budgets.json`, which a kind left out gets; `pnpm check:budgets` holds every registered variant and appearance pack to its budgets (Checking a variant, below). `stills` are your catalog stills, committed PNG or WebP files with their exact width and height, which a catalog plate shows before, and instead of, a live preview; `pnpm stills` shoots them, and they count toward `image`. `studio` is what Studio's composition picker says of it: `signature`, its idiom in up to 40 characters under its name, and `order`, a positive whole number the picker lists compositions by, lowest first, with those that have none after them; the host names no composition, so its place in the picker comes from here. Every field, with valid values, is in [`manifest-contract.md`](../skills/variant-developer/references/manifest-contract.md). A v1 field (`slug`, `themes`, `colorSchemes`, `typographyPresets`, `supportedKinds`, and the rest) is refused with where it went.

A variant may bind keys for widgets it owns in `keyBindings`, each `{ region, keys, action }` in a region of its own: lowercase letters, digits, the arrow keys, `PageUp`, `PageDown`, `Home`, and `End`. Contract 2.1 adds one document binding at most, for a command palette: `{ "region": "document", "keys": ["mod+k", "/"], "action": "palette.open" }`, where `mod` is Cmd on an Apple platform and Ctrl elsewhere, and its keys are `mod+k`, `/`, or both. A 2.0 manifest that declares it is refused. You only declare it: the host listens on the document, and your palette hears the action with `useDocumentAction('palette.open', open)` from `@portfolio/kit/runtime`, so your code touches neither the document nor storage. Mount one palette: the newest one mounted hears the action, so a second copy, such as one in a narrow screen's Menu, would take it. The binding never fires in an editable field (an input that takes text, a textarea, a select, contenteditable, or a textbox, searchbox, or combobox role), during an IME composition, with any other modifier (Shift alone may type `/`, and AltGr counts as a modifier), on a repeat, or in a document without focus, such as a Studio preview frame the owner isn't in. Where a page shows no visitor controls, as in Studio's and Demo Studio's previews and `/preview/dev`, only `mod+k` binds, since nothing there could turn `/` off, and a binding of `/` alone binds nothing. `mod+k` matches the K key on a layout whose k isn't a Latin letter, and `/` is the character wherever the layout puts it. Where your binding holds `/`, a single character, the host's visitor controls show a Single-key shortcuts toggle that turns it off (WCAG 2.1.4); the choice lasts in the site's localStorage, and for the page's life where storage is blocked, and `mod+k` stays. Open the palette from a button too, since a visitor may have neither key.

A contract 2.1 variant may opt in to cross-document view transitions (K-4 (a)): `"transitions": { "crossDocument": true, "names": ["<id>-hero", "<id>-title"] }`. Each name is `<id>-` and then lowercase letters, digits, and hyphens, ending in a letter or a digit; no name comes twice; there are at most 8 (`MAX_TRANSITION_NAMES`), since each named element is a snapshot the browser takes on every navigation; and with `"crossDocument": false` there are none. A 2.0 manifest that declares `transitions` is refused. Opted in, the host writes `@view-transition { navigation: auto; }` into your compiled stylesheet, after your layer and outside every cascade layer, and into no other variant's, so a navigation between two of your pages transitions, and one to another variant's page or to Studio doesn't. You never write `@view-transition` yourself (`audit.css-at-rule`). Give an element one of your names with `view-transition-name`, and animate it with `::view-transition-group()`, `::view-transition-image-pair()`, `::view-transition-old()`, or `::view-transition-new()` of that name: bare, or after `:root` or `html`, since the pseudo-elements hang from the document's root, or after `[data-variant='<id>']`, with `:only-child` at most after it. Anything else, `*`, `root`, a class, `view-transition-class`, a name your manifest doesn't list, and all of it in a variant that doesn't opt in, is refused (`audit.css-view-transition`). Durations and easing read the motion tokens, as anywhere else: the pseudo-elements inherit from `<html>`, not your boundary, so the selected scheme and language also give the root's `::view-transition` their `--color-*` and `--ui-motion-*` tokens. The host's rules come after yours, unlayered, so they win over your layered ones, in three motions. Under full motion, the page's own root crossfade, `::view-transition-group(root)`, `::view-transition-old(root)` and `::view-transition-new(root)`, runs at `--ui-motion-fast`, so the transition overlay, which holds pointer input, ends with the fade, and your named groups move as your stylesheet animates them; with no names, the root crossfade is the whole transition. Under reduced motion, `prefers-reduced-motion: reduce` or the boundary's `data-motion` `reduced` (the site's reduce policy, or a reduced preview), nothing moves or resizes: every group and image pair runs no animation, and every old and new image, root or yours, crossfades by opacity alone over `--ui-motion-fast`, in the host's own keyframes, which take the place of any wipe or clip-path you gave them. Under `data-motion` `static` (the pause), the change is an instant cut. The host's keyframes are named `_portfolio-vt-*`, which your keyframes can't be named and your animations can't run (`audit.css-keyframes`).

## The render path

```tsx
// src/index.tsx
import {
  renderSection,
  SharedFrame,
  VisitorControlSlot,
  type SectionComposition,
} from '@portfolio/kit/sections';
import type { VariantRenderInput } from '@portfolio/variant-contract';
import { Works } from './renderers/works';

/** The kinds in the manifest's renderedKinds, each with its renderer, and the frame around every section. */
const SECTIONS: SectionComposition = { renderers: { works: Works }, Frame: SharedFrame };

export default function AcmeOcean({ input }: { readonly input: VariantRenderInput }) {
  const { portfolio, ids } = input;
  return (
    <>
      <header className="ao-header">
        <VisitorControlSlot />
      </header>
      <main id={ids.main} className="ao-main" tabIndex={-1}>
        {portfolio.sections.map((section) => renderSection(section, input, SECTIONS))}
      </main>
    </>
  );
}
```

- It renders synchronously from the input alone, the same markup on the server, in #7's preview frame, and in #9's browser render.
- The input is the published view (#10). `input.portfolio` holds only what visitors may see, every list present: the sections, and the works, evidence, and chronology entries they reach. `input.media` has each placed asset, with its renditions or why it has none yet, and `input.derived` each github section's snapshot, or why it has none. A bespoke renderer finds a section's records with the kit's `worksOf(section, input)`, `evidenceOf`, and `chronologyOf`, and a placement's image with `placedMedia`, which adds the placement's caption, and when, where, and with what tags it was taken, for `MediaFigure` to render, as an `Image unavailable` box until a rendition exists.
- `input.appearance` (contract 2.1) names the packs that render the page, each by id and name: `{ scheme: { id, name }, language: { id, name }, typography: { id, name } }`, for credits such as a colophon. It's what the host's resolution decided, the visitor's choices and each axis's fallback applied, never what the site asked for, and it's the same on the server and in Studio's local frame, which resolve it from the same site and registry (`appearanceCredits` in `@portfolio/appearance`). It's read-only and frozen. Never style from it: the boundary's tokens do that. It's `null` only where a caller resolves no appearance, such as a unit test's input.
- It renders exactly one `<main id={input.ids.main}>` and exactly one `<VisitorControlSlot />`, which #19 fills.
- `renderSection` renders each section inside the composition's `Frame`, whose root, a `<section>` or an `<article>`, spreads the section's `FrameAttributes`: the id `${input.ids.prefix}${section.id}`, `data-section-id`, `data-kind`, `data-renderer` (`bespoke` or `shared`), the section's `lang`, and a `dir` when its language runs the other way, and renders nothing for a section with nothing public. A renderer map that disagrees with `renderedKinds` throws.
- An extension kind renders through the renderer its content extension registered, and renders nothing without one.
- Your navigation, case-study page, and footer are yours: `pageOutline(input)`, `caseStudyOutline(input)`, and `footerOutline(input)` give you what they read, and `composePages({ HomePage, CaseStudyPage, views })` makes your `.` export from your pages, `views` giving a view under home a page of its own (Routes, below). `pageOutline` lists a section exactly when `renderSection` renders it, so a link from it always lands. When one of your own elements holds a section's id, as Horizontal Cinema's chapters do, set the composition's `anchorOf` to give that section another anchor or none, pass the composition to `pageOutline` and `footerOutline`, and export it as `sections` from your `.` entry. The section's frame, the outline, and the outline check then agree on its anchor. `caseStudyOutline`'s part anchors are for a case-study page that heads each part itself; the shared `CaseStudy` writes none.
- Your persistent chrome never lists every section. `navigationModel(pageOutline(input, composition))` groups the outline into at most five destinations, each linking its section titled as the destination is labelled (About lands on the section called About), or else its first, plus the name linking home and the full `index` in reading order. The chrome is the name and those destinations; every section beyond them lives in your own index pattern, such as a margin index, a catalogue, a tile field, or a chapter scrubber.
- The destinations are the same five in every composition, so a visitor who switches looks finds each section where they left it. Their ids are fixed, and so is their order: `work`, `writing`, `record`, `about`, and `contact`, labelled Work, Writing, Record, About, and Contact by default, whatever order the page puts its sections in.
- Where each section goes is one canonical map, `CANONICAL_DESTINATIONS`, so "where is Publications" has one answer across every composition. It reads what a section is, `sectionClass(section)`: its kind, and what its items are (`works:writing` for works that are all writing or research, `evidence:<type>` for evidence of one type, `practice:<part>`), never its title or id. `model.placed` gives every section's place by content id.
  - Work: works sections, Incident History among them.
  - Writing: a works section that's all writing or research, Essays among them. Nothing moves one.
  - Record: evidence of every type, Publications, Talks and Press included; GitHub; chronology. So On GitHub is Record.
  - About: a titled lede; practice, Skills and Tools included; focus, now, quotes, and fun facts.
  - Contact: contact and calls to action.
  - The index alone: the hero, an untitled lede, and custom and extension sections.
- You move a section only by declaring overrides, and only with a test. Declare them as a named constant with `defineNavigationOverrides({...})`, keyed by class or by kind (a kind names all its classes, the class winning), such as `const PLACE = defineNavigationOverrides({ 'evidence:publication': 'writing', 'practice:skills': 'record' })`, and pass it as `overrides`. `navigationModel()` takes no other map: a plain object, a copy or a spread of one, or a cast fails the type and throws. Then test the constant: `checkDestinationOverrides(PLACE, outlines)`, with the sample's and the contract fixtures' outlines, expecting `[]`. It reports a key that's no class, a destination that's none of the five, an attempt to move writing works, an entry that sends every section it matches where it would go without it, and one that matches no section with an anchor. `pnpm test:quality` fails a package with a `defineNavigationOverrides()` call that isn't a named constant, or that no test checks.
- An `evidence:<type>` key matches a section only while every entry it shows is that type: once the owner adds a talk to Publications, the section is plain `evidence`, the key no longer moves it, and it goes to Record. Name the kind, `evidence`, to move every evidence section.
- If your composition has its own boards or sheets, declare them with `grouping`. Each group stands for one of the five ids, and `groupOf(section, context)` says which sections go where (the context gives the section's place, class, position, and whether it's the first of its kind or class). Grouping is for display alone and never moves a section to another destination: a board may split one destination's sections, or hold them with the sections the map leaves to the index, but a section's chrome link and index group stay the map's.
  - A section `groupOf` puts in a group standing for another destination is refused: it goes to its own destination's home group, and `model.diagnostics` says so. The kit reads no environment and doesn't log, so show the diagnostics in your development view, and test with `checkGrouping(options, outlines)` on the sample and the contract fixtures, expecting `[]`. `pnpm test:quality` fails a package that declares `groupOf` without that test.
  - A section `groupOf` leaves goes to its destination's home group: the group named after the destination, else the only one that stands for it.
  - A destination with no group leaves its sections in none, with a diagnostic too, so declare a group for every destination the page may have, such as a Writing board, which drops while it's empty.
  - A section the map leaves to the index (the hero, an untitled lede, custom and extension sections) may go in any group, else in `unplaced`, else none. `groupOf` returns `null` to leave a section out of every group.
  - A mistake in the declaration throws: an id twice, a destination that's none of the five, two groups for one destination with neither named after it, or an `unplaced` or `groupOf` answer that's no group.
  - `model.groups` lists the groups in your order, none empty, sections in reading order. Without `grouping`, it's every destination with sections.
- Relabel a destination for your metaphor with `labels`, such as `{ record: { text: 'Craft' } }`; never rename, add, or drop one. Your words are English unless you give `lang`, so they're marked `lang="en"` in a portfolio that isn't, as the defaults are. The owner's own words go in `ownLabels`, in the portfolio's language, and win. Writing is always a destination when the page has a writing works section, and the one `primary` keeps first when you ask for fewer.
- On a narrow screen, the chrome is the name and a Menu: render `<NavigationMenuSlot id label href visitorControl>` with your own links as its children, never a Menu of your own. Lead the children with the destinations as large links, so Writing and Contact are in the first view, and keep the full index after them or behind one disclosure. The host fills the slot with #19's Dialog: its title and close button stay in view as the links scroll (`closeInHeader`), a tap on the backdrop closes it (`lightDismiss`, `closedby="any"`), and following a link to a place on the page closes it and moves focus there (`closeOnNavigate`). With `visitorControl={{ media }}`, the media query under which you show the Menu, the visitor's appearance control moves out of your `VisitorControlSlot` into the Menu, at its end, so the chrome is the name and the Menu alone. Your composition stays a server module. Where no host fills it, as in a render outside the host, and where scripts don't run, it's a plain link to `href`, which should be your index on the page, so every section stays a real link away, and the control stays in its slot. `id` is a local id no content id takes; the fallback's `menuId` shows one way to pick it.
- Your page ends on one closing block, never on a contact section and then a call to action. `footerOutline(input).cta` is the call to action beside the contact section, with its title, description, and primary and secondary actions: merge it into your closing form under one heading and one message, lead with its primary action, and leave the section out of your reading order. The contact's title is the block's one heading, and the call to action's title opens its message, so every title the owner wrote shows and none is a second heading. `footerOutline` lists every link target once: the call to action's actions keep their labels, `email` keeps the address for you to show as text beside an action that mails it, and `links` and `contact.links` leave out anything those already reach, so a "Resume" link to the CV the "Download CV" action opens isn't listed again. Put any index before the closing block, so the page ends on the invitation.
- `checkOutline(html, input.ids, { sections })`, in `@portfolio/variant-contract/node`, holds your markup to one `h1`, the skip link's focusable `main`, headings that never skip a level, a frame for every section the page renders (`sections` is `pageOutline(input, composition).sections` on home) carrying its anchor, named navigation landmarks, and real links. `apps/web/src/lib/composition-outline.test.tsx` runs it over every registered composition, contract fixture, and route, and lists every finding it expects today, with why.
- Markdown goes through `RichText`; anything random-looking through `seededRandom(input.env.seed)`; the time is `input.env.now`. The seed follows the visible content alone, leaving out the times the server takes from its clock (a derived record's `derivedAt`, a GitHub snapshot's `fetchedAt`), so a seeded picture is the same at every start.

## What the host does around it

- The document boundary, `<div data-appearance-boundary="document" data-variant="<id>" data-display-mode="..." data-motion="..." ...>`, with its skip link to `#<input.ids.main>` first and the variant inside. #19's tokens apply at the boundary, and so does the variant's stylesheet. The 404 page renders inside the same boundary.
- When the site selects a variant this build doesn't register, the **fallback composition** renders in its place with a 200, and the boundary carries `data-requested-variant`. Startup logs a `variant.unavailable` warning, `config.status` reports `variant: { status: 'degraded', requested, rendered: 'fallback' }`, and `/api/ready`'s `packs` check says `degraded`. Visitors see no label. #3's publish refuses the selection.
- Under the demo profile, `/sample` renders the bundled sample in the sample site's selection, and `/sample?variant=<id>` in any registered variant. `fallback`, an unregistered id, an empty one, or two are a 404.
- While `isServable()` is false, which #3's catalog sets when it has nothing to serve, visitor pages answer a static 503 with `Retry-After: 120` and `X-Robots-Tag: noindex`.

## Routes

The host owns every route, and asks `dispatch()` what each path is, against the composition that renders:

- `/` is home, and `/work/<slug>` a work's case study: one the live revision publishes, on a public work a visible section reaches. Any other slug is the 404 page. A variant whose manifest says `routes.work: bespoke` renders that page itself, and `routedWork(input)` from `@portfolio/kit/sections` is the work the route names. One that says `shared` leaves it to the host, which renders it through the fallback composition: the kit's `CaseStudy` as the page's one h1, and a link home. So every composition has case-study pages, and none shows its home at a work's address. The views a variant declares under `work` stay its own.
- A path view the manifest declares renders below its parent route, such as `/chapters/<chapter>` or `/work/<slug>/notes`, from the server, so it works without JavaScript and after a refresh. It carries a canonical link to its parent route at the site root, none under `/sample` or in a preview frame, and stays out of the sitemap. A view the site document's `routes` turns off is the 404 page.
- A placeholder takes one segment of lowercase words joined by hyphens, at most 64 characters, as a content id does. A longer value is no view. Any value that fits renders the view, whether or not it names anything: a way for a view to answer 404 for one that names nothing is a later addition to the contract.
- Until then, `composePages()` answers for you. Give a view under home its page in `views`, by view id: a component, such as `'back-matter': BackMatterPage`, or `{ Page, known, unknown }`, such as `chapters: { Page: ChapterPage, known: (input, { chapter }) => ..., unknown: 'No chapter by that name.' }`. A value `known` refuses renders your `HomePage` with `notice`, the view, its parameters, and the note, which defaults to "No <view id> by that name.", and the page is `noindex`, with no canonical link, since the two together say different things. The status stays 200. A view with a placeholder needs `known`: without it, its page renders for any value that fits, one that names nothing too. A view you name no page for renders `HomePage`, as before.
- A path only another installed variant declares is a 307 to its parent route, so a bookmark from before a switch lands home, not on a 404.
- Anything else is the 404 page.
- Under `demo`, the same routes sit below `/sample`, and `?variant=<id>` stays on every link and redirect.

Link to a route with `routeHref(input, target)` from `@portfolio/variant-contract`. It writes the URL below `input.basePath`, keeps `input.query`, and puts `input.ids.prefix` on a fragment view's id, so one render links right at `/`, below `/sample`, and below #7's preview prefix. The kit's shared renderers do the same for a `/#section` link.

A path view can't start with a segment the host owns: `studio`, `api`, `_next`, `_fixtures`, `sample`, `reference`, `preview`, `preview-assets`, `work`, `admin`, `variants`, and the metadata files. Generation fails on one, and the root catch-all leaves each to its own route, so a view never shadows an API or metadata route.

The route table knows from the build's manifests, before any page runs, which paths name nothing: one no installed variant declares, a slug the live revision doesn't route (#10b, the one answer it reads from the live site), a placeholder value over 64 characters, or a `?variant=` that names nothing. Each gets the 404 page from the server, with its 404 status, so it works without JavaScript. One 404 still draws in the browser: a view the live variant declares and the site document's `routes` turns off. Next 16 answers a page's `notFound()` with an error document the browser fills in, so without JavaScript that page is empty; the status is 404 either way.

## Compatibility

Every check of a pair against the composition that renders it is one report, `compatibilityFor(pair, { registry })` from `@portfolio/variant-contract`. Startup and `pnpm config:validate` get its findings as diagnostics, and so will #3's publish. It needs nothing from Node, so #9 can run the same code in the browser. `evaluateCompatibility(manifest, pair, { registry })` reports on a candidate as if the site selected it, so #8 and #9 can explain one before the owner switches. The report has:

- `variant`: what the site selects, what renders (the selection, or the fallback composition in its place), and its package version. In a candidate's report both name the candidate, and a `variant.unavailable` there says what selecting it would render.
- `kinds`: each visible kind and how it renders: `bespoke`, `shared`, through its content extension's renderer, `unsupported`, or `none`.
- `slots`: each content slot's fill count, with its `whenEmpty` note when it has fewer than it asks for.
- `routes`: the previous variant's path views this one doesn't serve. Each redirects to its parent route while the previous variant stays installed, and is a 404 once it's removed.
- `inputHash`, of everything the report depends on, and `status`: `ok`, `warning`, or `blocks-publish`.

| Finding                                                            | Code                                                          | Preview                                 | Publish |
| ------------------------------------------------------------------ | ------------------------------------------------------------- | --------------------------------------- | ------- |
| The selected variant isn't registered                              | `variant.unavailable`                                         | the fallback composition renders        | blocked |
| A required slot holds fewer than its `min`                         | `slot.required-empty`                                         | renders, as the slot's `whenEmpty` says | blocked |
| A recommended slot is empty                                        | `slot.recommended-empty`                                      | renders, as `whenEmpty` says            | allowed |
| A slot holds more than its `max`                                   | `slot.overflow`                                               | the extras render after the slot        | allowed |
| A visible section of an `unsupportedKinds` kind                    | `kind.unsupported`                                            | visitors don't see it                   | allowed |
| A visible extension section nothing renders                        | `kind.no-renderer`                                            | the rest of the page renders            | blocked |
| A stored control value that's invalid, stale, or points at nothing | `controls.invalid`, `controls.stale`, `controls.dangling-ref` | the control renders its default         | blocked |
| Right-to-left content in a variant that declares only `ltr`        | `direction.unsupported`                                       | renders left to right                   | allowed |
| A `recommendedAppearance` this build doesn't list                  | `appearance.unknown-recipe`                                   | the site's own appearance renders       | allowed |

An empty optional slot shows only in `slots`. A slot counts the visible sections of its kind, the visible sections or records its control points at, or the values its field holds in the published view, an array counting each item. Startup checks the pair as live, so a finding that blocks publishing only warns there: something renders in its place either way.

After a variant raises its controls version, `pnpm variants:migrate-controls --site config/site.yml` steps the stored values through the manifest's migrations. It prints each change and a diff, and writes only with `--write`, through a symbolic link to the file the link names, keeping that file's mode, owner, and group, so the server's user reads it as before. Once it has written, a second run finds nothing to do. It writes nothing and exits 1 for a link whose file is named for the other format, or a file whose owner and group the user running it can't give a new file. Values of another version are never read: until they migrate, every control renders its default.

A YAML document keeps every line the migration doesn't change, comments included. A renamed control moves to the end of its `values` mapping, and a key or value the migration writes is plain, or double-quoted when it must be, whatever quotes the document used. A JSON document is written whole, in its own indent with one value per line, so a document already in that layout, as `JSON.stringify` writes it, changes only in the entries that migrate. YAML the edits can't change in place, such as a complex key (`? key`), stops the command with exit status 1 and the file as it was.

## Motion

The site's policy reaches a variant as `input.presentation.motionPolicy`: `respect-os` follows the visitor's `prefers-reduced-motion`, and `reduce` always reduces. The boundary carries the motion that renders as `data-motion`: `reduced` under `reduce` or a preview's reduced environment, `static` in a plate or once the visitor pauses motion, and `full` otherwise, when the visitor's `prefers-reduced-motion` decides. Its `--ui-motion-*` and state tokens follow all of them, so a stylesheet takes its timing and movement from the tokens and stops motion of its own under `[data-variant='<id>']:is([data-motion='reduced'], [data-motion='static'])`, never with a universal `!important` kill switch ([`styling-conventions.md`](../skills/variant-developer/references/styling-conventions.md)).

CSS rules don't reach motion that scripts run. Wrap the variant's client parts in `MotionPolicyProvider` with the policy, and run every script effect on `@portfolio/kit/runtime` (#6): attach `useEnhancementRuntime()`'s `attachRoot` to the effect's root, draw frames through `useFrameLoop(runtime, draw)`, and render the still while `runtime.state` is `static`. The runtime keeps it static before the page mounts and under reduced motion, and pauses it while the document is hidden, the root is offscreen, the visitor paused motion with `MotionControl`, or a Studio preview frame is out of focus; a root that isn't active carries `data-activity="paused"`, which pauses its CSS animations. The kit's own effects already run on it. Load an enhancement with `EnhancementIsland`, which renders your server markup, loads the chunk only while the runtime is active, and falls back to that markup if it fails. Scroll with `behavior: 'auto'` under reduce. [`common-bugs.md`](../skills/variant-developer/references/common-bugs.md) section 8 has the details.

An ambient loop, one that runs as long as the page shows, such as a sky's drift or blobs that merge, takes its cycle from the ambient slot (contract 2.1): set `--layout-motion-ambient`, 20 to 60 s, in your root rule, and run the loop as `animation: <id>-drift var(--motion-ambient) linear infinite; animation-play-state: var(--motion-ambient-state)`. The state pauses the loop under reduced motion, `static`, print, and in a runtime root that isn't active, so put the loop inside an element attached to a runtime's `attachRoot` for the visitor's pause to reach it. A page gated from the start, a plate, print, or reduced motion at load, shows the loop's first frame; a pause mid-run holds whatever frame it's on, so every frame has to read as a still, or swap in your still under `data-activity="paused"` ([Appearance](appearance.md#shared-scales)). The source audit's `motion-gate` rule refuses an infinite loop (an `infinite` iteration count, or more than 1000) whose rule doesn't set `animation-play-state: var(--motion-ambient-state)` after its last `animation` shorthand, under `[data-kit-runtime]` too: the runtime's pause reaches a loop only through the state, and leaves a one-shot entrance to play to its end, so no selector stands in for it. The kit's runtime sets `[data-kit-runtime]`, `active` or `paused`, on the element attached to `attachRoot` while the runtime may run, and never on the server, before mount, under reduced motion, in a plate, or once it failed, so a loop under it, as Kinetic Cosmos's stage loops are, never starts before then. Only the kit sets it: a variant setting it in any way, a computed name included, is out of contract, and the audit refuses its name in a variant's code. It refuses `animation-play-state: running` anywhere.

`budgets.animation` counts what keeps running while the page sits idle: frame loops, recurring timers, and infinite animations, one each. A finite animation, such as a reveal, ends, and a scroll-driven one (`animation-timeline: scroll()`, `view()`, or a named timeline) does no work until the visitor scrolls, so neither counts (RB ruling R3); `pnpm check:budgets` counts the trace's on these terms, and a pack's from its stylesheet. Put a scroll-driven loop under `@supports (animation-timeline: scroll())`, or give it a finite count: a browser without scroll timelines drops the timeline and runs it on the clock, and the stylesheet count only takes it off the clock under that guard. Any other timeline, `auto`, a CSS-wide keyword, or a `var()`, is the clock, and a list counts its items on the clock. What the count can't be talked out of: an iteration count over 1000, in any numeric form (`1e6` included), counts as infinite, and so does a running animation with more than 30 s left; a Web Animation that restarts itself when it finishes (by `animate()` again, `play()`, `reverse()`, or a seek on `currentTime`) counts as a recurring site; a CSS animation or transition a handler starts again on one element, by a class toggled on `animationend`, counts once its start events fall in both halves of the trace's window; and `requestIdleCallback` and `scheduler.postTask` loops count as recurring timers. A loop driven by `MessageChannel` or `postMessage`, SVG SMIL (`repeatCount="indefinite"`), and looping autoplay video are outside what the trace sees, so build no ticker or clock on them; the backlog has the check. A first-party composition declares the count `FIRST_PARTY_ANIMATIONS` approves, and `check:variants` refuses another: Aurora Glass 2, Raw Grid 1, Mission Control 1 (the minute clock), Flux at most 3, Kinetic Cosmos 3, Spatial Bento 1, and 0 for every other.

`tests/trace/modes.spec.ts` traces `fixture-variant-medium` in each mode, with `pnpm test:trace` after a `BUDGET_FIXTURES=1` build: running, hidden, offscreen, the OS's reduced motion, the site's `reduce` policy, the visitor's pause and resume, a preview frame out of focus, no WebGL2, a failed enhancement chunk, and blocked fonts, media, and stylesheets, each holding the page for 5 seconds and counting frame loops, recurring timers, and infinite animations, with the page reading the same as without JavaScript and its layout shift recorded.

`tests/e2e/motion-contract.spec.ts` checks every registered composition: under `reduce`, and under `respect-os` with the visitor's reduced-motion setting, no animation runs once the page settles, after a navigation link's jump, or as each part of the page scrolls into view; no script keeps asking for animation frames; and the link jumps to its section, in the window or in a scroll container of the composition's own. A canvas drawn without `requestAnimationFrame` is outside what it sees. `tests/e2e/motion-harness.spec.ts` shows each check catching what it's for. A variant passes it before it registers.

## Styling conventions

A variant composes and designs its elements; the appearance axes (#19) supply every value it uses. Color comes from the color scheme, materials, the geometry tokens, states, and timing from the design language, and text from the typography profile, all as custom properties on the presentation boundary the host renders around you. [Appearance](appearance.md) is the contract: who owns what, the tokens, the boundary, the layer order, and the shared primitives.

- **Layout and element design.** Spacing, arrangement, grid and flow, sizing, order, how structure responds to the viewport, and how each of your own components and elements looks. The owner defined the axis this way: a composition "decides component and element design as well as layout". So, in your own markup and CSS, you may:
  - pick, for each component, among the language's tokens: radius `none` or `var(--ui-radius-control|card|media|overlay|badge)`, or a circle, `var(--layout-round)` with `--layout-round: 50%` declared; border `var(--ui-border-divider|control|card)`; and shadow `none` or a `var(--ui-shadow-*)` layer;
  - draw your own lines as `--layout-line-*` and `--layout-rule-*`: by convention border shorthands of a px width, `solid` or `dashed`, and a role color, `currentColor`, or a `color-mix()` of roles, such as `--layout-line-hair: 1px solid color-mix(in oklab, var(--color-border-strong) 26%, var(--color-canvas))`. The source audit's `layout-line` rule holds those names to that form; a border written another way isn't refused, but keep your lines in them. A name ending in `-height`, `-size`, `-length`, `-clamp`, or `-gap`, such as `--layout-line-height`, is geometry, not a line, and the rule leaves it alone;
  - mask or clip a `::before` or `::after`, a mask naming black, white, and transparent, which it reads for their alpha alone, and give one empty generated content (`content: ''`);
  - size text as a `calc()` multiple of a step or a role's size, such as `calc(var(--type-step-5) * 1.6)`, or set the code role's family at the body role's size;
  - use `:has()`, `initial-letter`, and a scroll-driven `animation-timeline`;
  - size text from `var(--type-step-*)` and the role weights, never a family;
  - place role surfaces: the canvas and `--color-surface-*`; the inverse pair (ground `--color-text-primary`, ink `--color-text-inverse`); the matte pair (`--color-scrim`, `--color-on-scrim`); accent and `on-accent`; and a `color-mix(in oklab, …)` of two role tokens for hairlines and tints ([Surface pairings](appearance.md#surface-pairings));
  - declare `--layout-*` properties for your own geometry, such as masks, clip-paths, aspect ratios, and grid areas;
  - choreograph motion through `var(--motion-*)` alone.

  The packs keep every color value and font family, materials (texture, grain, blur, glass), focus and state colors, and the `[data-ui-slot]` parts of the shared primitives. A composition that wants a different control builds its own element; it never restyles a primitive's slots. Your stylesheet compiles into the `variant-layout` layer, above the packs and below the utilities and accessibility layers.

- **Read the tokens for everything else.** Every color is a `var(--color-<role>)`, such as `--color-text-secondary` for quiet text, never a lower opacity. Every border, radius, and shadow is a `var(--ui-<key>)`, such as `--ui-border-divider` or `--ui-radius-media`, and every duration and easing a `--ui-motion-*`. Text takes a role with `data-type-role="<role>"` in your markup, such as `display` or `caption`, or reads `var(--type-<role>-<field>)` in a rule. The only custom properties you define are `--layout-*`: both audits refuse a declaration in the platform's namespaces, `--color-*`, `--ui-*`, `--type-*`, `--space-*`, `--motion-*`, and `--rhythm-*`, such as your own `--ui-acme-glow` or a redefined `--color-accent`, but for the platform properties `COMPOSITION_SETTABLE` in `@portfolio/variant-contract` names (none yet). A radius, a shadow, a duration, or a color reads a token only by a name the platform defines, `PLATFORM_TOKENS` there, so a token of your own, declared or not, is no token. A `-webkit-` or other vendor prefix doesn't hide a shadow or a radius, and a named color is a color in any image value, such as `border-image` or `mask-image`.
- **Space and size from the shared scales.** Padding, margins, and gaps read `var(--space-*)`, a fluid pair, or the `--layout-grid-*` and `--layout-width-*` values, never a px, rem, or vw length of your own. Durations and easing read `var(--motion-*)`. Set the grid, the widths, and your `--layout-motion-*` slots in your root rule, `[data-variant='<id>']`, alone, or on the root with attribute selectors of your own, such as `[data-variant='<id>'][data-tf-field='quiet']`, under `@media`, `@layer`, `@supports`, or a `@container` size query if you need one, and under no other at-rule: in `@scope`, a `@container style()` query, or `@supports selector()`, the rule isn't your root rule any more. Never select on an attribute the platform sets: the boundary's, which `isPlatformAttribute()` in `@portfolio/appearance` lists (the pack ids, the display mode, contrast, motion, `data-enhancement`, `data-mode-locked`, `data-requested-*`, and `data-appearance-*`), or the kit runtime's. Your composition doesn't render the boundary element, so such an attribute reaches it only from your code after the first paint, which renders the root rule's own values. Other `--layout-*` properties may go under any selector, such as `[data-variant='<id>'] .tile[data-span='10']`. [Appearance](appearance.md#shared-scales) lists them. The space lint in `packages/appearance/src/node/space-lint.test.ts` reports each length a composition sets itself, reading a grid, width, or motion slot your root rule sets as the platform's default and the same slot on a descendant as a length of your own. The type lint in `type-lint.test.ts` reports each font size that isn't a `var(--type-step-*)` or a role's size. The translucency lint in `translucency-lint.test.ts` reports each background you make translucent yourself: a `color-mix()` with `transparent`, a `color-mix()` whose weights add up to less than 100%, a relative color with an alpha below 1, an `opacity` between 0 and 1 under a selector that paints a background, or a material token, such as `var(--ui-surface-material)`, with no surface layer over it. Such a pane never meets the language's 97% glass floor, so paint panes through the language's surface stack, a surface at `var(--ui-surface-opacity)` over `var(--ui-surface-material)`, which it skips. A dialog's `::backdrop` is a scrim, see-through on purpose, and passes too. All three are todos until the compositions move over, and the translucency lint refuses once they're clean. Horizontal Cinema's prologue title card is the one size a composition may set itself: its name fills the card's measure in `cqi`.
- **Use the shared primitives** from `@portfolio/appearance/primitives` for actions, surfaces, disclosures, badges, fields, and the rest: you choose which goes where and with what emphasis, and the packs style them. Native elements come first.
- **No appearance of your own.** A raw color (`#hex`, `rgb()`, `oklch()`, a named color), a `font-family` or `font`, a `@font-face`, a border radius, or a shadow is refused unless it reads a `var(--...)` token; `currentColor`, `transparent`, a zero radius, `none`, and CSS-wide keywords are fine. A `font-family` is a `var(--type-<role>-font-family)` token, a generic family such as `monospace`, or `inherit`, and a `font` shorthand reads only `--type-*` tokens. A duration or a delay, a `-webkit-` one too, reads `var(--motion-*)`, `var(--ui-motion-*)`, or one of the four `--layout-motion-*` slots, or is 0; a `calc()` may scale a token by a factor up to 4; and an infinite loop's cycle reads the ambient slot, `var(--motion-ambient)`, never a scaled UI token. A slot holds a value in its band. `attr()` goes in `content` alone, as a plain `attr(<name>)`. A system color, such as `Canvas` or `Highlight`, goes under `@media (forced-colors: active)` alone, and `hue-rotate()`, `sepia()`, `saturate()`, and `invert()` read a `var(--ui-*)` token; `grayscale()` is fine. `!important` is refused (`audit.css-important`): it would win over the accessibility layer.

The variant audit, the gate a third-party package meets, reads your stylesheet with PostCSS on a strict grammar, so nothing reads one way to it and another to a browser. A stylesheet PostCSS can't parse is refused (`audit.css-syntax`), and so is a comment in a selector or an at-rule prelude: put it on its own line above the rule. The scope's compound comes first in every selector, and a descendant or `>` follows it: `[data-variant='<id>'] ~ *`, `+ *`, and `[data-variant='<id>']:has(~ *)` reach its siblings and are refused (`audit.css-unscoped`), while `~` and `+` between your own elements inside it are fine. Six at-rules go in your stylesheet: `@media`, `@supports`, `@layer`, `@container`, `@keyframes`, and `@import`. Any other, `@scope`, `@font-face`, `@property`, `@counter-style`, `@page`, `@font-feature-values`, `@starting-style`, or one the audit doesn't know, is refused (`audit.css-at-rule`), and `pnpm check:appearance` refuses it in the platform's own compositions too (`at-rule`). So is `@view-transition`, which the host writes for a variant that opts in (above). A `@supports selector()` tests one compound of pseudo-classes and pseudo-elements, such as `selector(:popover-open)` or `not selector(::details-content)`: no combinator, `&`, type, attribute, class, id, argument list, comment, or escape. A backslash is refused anywhere, in a name, a selector, a value, or a string (`audit.css-escape`); write the character itself. The platform's own packages alone may name a printable character in a `content` string as `\<hex>`, such as `'\201C'`, which their scope, not the stylesheet, decides. A string goes in `content`, `font-feature-settings`, `font-variation-settings`, a quoted `url()`, and `grid-template-areas`, `grid-template`, and `grid`, whose strings name areas alone (letters, digits, `_`, `-`, `.`, and spaces), and nowhere else (`audit.css-string`). A `url()` and an `@import` name a quoted path inside the package, such as `url('./mark.svg')`: no unquoted `url()`, scheme, `data:`, `//`, `%`, or `var()`, and an `image-set()` takes `url()`s alone. A `clip-path` or a `shape-outside` with `round` in `inset()`, `rect()`, or `xywh()` gives a corner, so it's a radius too: `round var(--ui-radius-*)` or `round 0`. `circle(50%)` gives none. No theme blocks, no display-mode selectors, and no theme toggle: the visitor's appearance control renders in your `VisitorControlSlot`.

- **Scope every selector under `[data-variant='<id>']`,** and reach only what's inside it: no `+` or `~` after the scope, nested rules included. Your stylesheet loads only on the pages that render you, but a page can show another variant's boundary too, such as a catalog plate, so the scope keeps yours to your own. Never key a rule on a pack's attribute, such as `[data-color-scheme]`: a composition reads the same under every pack.
- **Reduced motion is the boundary's.** It carries `data-motion`: `full`, `reduced`, or `static`. Under `reduced` the state transforms read `none` and entrances, exits, and emphasis stop moving, but the durations stay; only `static` zeroes them. So motion on the tokens needs nothing more, and a keyframe animation of your own has to stop under `[data-variant='<id>']:is([data-motion='reduced'], [data-motion='static'])`.
- **Name keyframes after your id,** as `<id>-name`, so no other stylesheet shares the name.
- **Logical properties** (`margin-inline-start`, `inset-inline-end`, `text-align: start`), so a right-to-left page mirrors. A variant that declares `rtl` must use them.
- **One stylesheet**, the `./styles.css` export. No CSS imported from modules, no `@import` but your own files by relative path, no `url()` on another host, and no `<style>`, `<link>`, or `<script>` rendered from a component.
- **BEM-style classes** with a short prefix of your own: `<prefix>-<block>__<element>--<modifier>`.

Judge a variant under more than one selection: the same layout should hold under every design language, color scheme, typography profile, and display mode. The full conventions are in [`styling-conventions.md`](../skills/variant-developer/references/styling-conventions.md).

## Checking a variant

```sh
pnpm check:variants --package @portfolio/variant-my-id
```

It generates the registry, as `build:registry` does, then audits the variant's source and styles, every `@portfolio/kit` entry the variant imports (and `@portfolio/kit/sections`, which renders its sections) with each kit module those import for the clock and randomness rules, and the kit's shared stylesheet for appearance. Without `--package` it audits every registered variant. Any error or finding fails it, with the file, the line, and the fix; when generation fails, every error shows, whichever package it names.

The audit is a lint over code the host already trusts, not a sandbox: a variant installs at build time with full server trust, and a determined package can get around any syntax check. It reads each file's syntax, follows the globals it reaches for through aliases, destructuring, string keys, and `Reflect.get`, and refuses what it can't follow, such as a computed key or the global object passed around.

The audit refuses `async` components (by name, as a default export, or wrapped in `memo()`; an async event handler is fine); Node built-ins, `server-only`, `next`, `@portfolio/core`, and an import from a URL; `process`, `process.getBuiltinModule()` included; the kit's `fetchGitHubData`; `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, and `navigator.sendBeacon`; cookies, Web Storage, `indexedDB`, and the Cache API; `Date.now()`, `Date()`, argument-less `new Date()`, `performance.now()`, and a date format's `format()` with no date; `Math.random()`, `crypto.getRandomValues()`, and `crypto.randomUUID()`; `eval`, `Function`, and a timer given a string; `import()` and `require()` of anything but a literal; `dangerouslySetInnerHTML`, `innerHTML`, and `document.write()`; a `<style>`, `<link>`, or `<script>`; CSS imported from a module; a `'use client'` component that takes the whole render input or a prop named `input`, other than a declared enhancement (a `Pick<>` of it, or one field such as `VariantRenderInput['env']`, is fine); a selector or page-wide at-rule outside `[data-variant='<id>']`, or one that reaches a sibling of it; keyframes not named after the id; a remote `@import` or `url()`, or an `@import` of another package; a raw color, font, radius, or shadow; and, in a variant that declares `rtl`, physical properties and shorthands, keyframes included.

One clock read is allowed outside that list, on purpose: `document.timeline.currentTime`, read in an effect after hydration only to decide whether a finite load animation plays, so it never chooses markup (Spatial Bento's settle skips a late hydration with it). Anything that renders from the time still uses `input.env.now`.

CI runs it in a job of its own, `check-variants`. `pnpm check:registry` checks that two registry builds match and that nothing generated is committed.

```sh
PORTFOLIO_ANALYZE=1 pnpm build && pnpm test:trace && pnpm check:budgets
```

`pnpm check:budgets` holds the variant to its `budgets`, from the build output, `ASSET_MANIFEST`, and the trace: its compiled stylesheet, its image and font files, its own JavaScript on each traced route, the loops, timers, and infinite animations an idle page runs, and every chunk each enhancement's import loads, whole, a library's included. Each breach is a failure record naming the metric, the route, the asset that carries the most of it, the actual, and the limit, in `reports/budgets/budget-report.json`. A budget declared over its tier's ceiling fails too, as does a remote `@import` or `url()` in its stylesheet. CI's `trace` job runs it over every registered variant, beside the budget fixtures.

The compiled stylesheet includes the kit's shared layout, `@portfolio/kit/sections/styles.css`, about 1.4 KB gzipped, so it counts against `budgets.css` before a line of the variant's own: a light-tier variant at 2048 B starts with about 600 B of room. `apps/web/scripts/variant-css-budgets.test.ts` compiles every variant the host depends on the way the budget check measures it, so a kit change that pushes one over fails in `pnpm -r test` first.

The variant specs in `tests/variants/` start the production build once for each registered composition on each contract fixture, under `read-only`, and once on the bundled sample at `/sample`, under `demo`. The fixtures are in `packages/variant-contract/fixtures/`, and `@portfolio/variant-contract/node` exports them as `CONTRACT_FIXTURES`: #4's profession pairs, plus `complete` (every core kind and record type, with media of every kind), `identity-only`, `sparse`, `large` (100 works, 100 photos, and 100 skills), `long-text` (long, non-Latin, and duplicate titles), `missing-media`, `rtl`, and `hidden-canary`. Only `hidden-canary` has a snapshot beside it, `snapshots/github.json`, which the specs hand the server too; every other `github` section shows the profile link alone. The specs mount no media root, so no fixture's asset has a rendition, and every image renders as `Image unavailable`, and a decorative one as nothing. The bundled sample's do: `demo` derives them from `example-media/` once it starts, and the sample specs wait for that before their first check. Each selects `missing-variant`, and the specs select the variant under test. The server's clock starts at 2026-01-01T00:00:00Z and keeps running, from a `NODE_OPTIONS=--import` preload, `tests/harness/fixed-clock.mjs`. Each fixture's sitemap, modified per request, shows that date, and so does every line the sample's server logs, since demo's sitemap lists nothing.

Each fixture runs in six modes: desktop (1440x900), mobile (390x844), no JavaScript, print, failed enhancement, and reduced motion. In every mode the page has one presentation boundary, the variant under test's, and one `h1`, one `main`, and one visitor-control slot; the skip link moves focus to `main`; nothing is wider than the window; every internal link answers; each section's `data-renderer` matches `renderedKinds`, and none is of a kind in `unsupportedKinds`; and the console shows no error. Without JavaScript, in print, and with the enhancements failing (every script chunk blocked while the stylesheets load, then the kit's throw switch, which must fail every enhancement the kit mounts on the page), the `h1`, the navigation, and each section's heading have a box, opacity, and visibility. A nav's box is its links', clipped to the nav, so links placed outside a nav with no height still count. Print also has nothing fixed or sticky, and under reduced motion nothing runs once the page settles.

The throw-switch run waits for the page to go idle, for up to about 15 s while it stays busy, and then needs the counts to hold for a second. So it catches an enhancement that mounts within about a second of idle, but not one that mounts later. A count of pending mounts for the check to wait on is in #6's backlog. On `complete`, which renders every kind, the kit also has to mount at least one enhancement when the manifest declares one with an empty `requires`, so the check can't pass by counting none. Such a composition renders one on its home page, where it mounts as the page hydrates, with no scrolling or input. One whose only such enhancements live on a path view, or mount once they're scrolled into view, fails the failed-enhancement mode on `complete`. An enhancement that needs a capability lists it in `requires` (headless Chromium may lack `webgl2`), and the floor leaves it out.

`hidden-canary` hides sections, the records, media, practice parts, contact record, and snapshot only they reach, private records and media wherever they're named, and a repository its visible github section excludes, each carrying a marker, which reaches neither the HTML, its JSON-LD, the RSC payload, nor the feed. Its two case studies, a private work's and one only a hidden section reaches, have no page. On every fixture, each case study the sitemap lists renders at `/work/<slug>` with its title as the one h1, without JavaScript, and any other slug answers every method as `/no-such-page` does, as a page and as an RSC request. Render parity compares the boundary in the host's server HTML with a `react-dom/server` render outside Next and a `createRoot` render in a test page, all from one render input at the fixed time, as the tags, text, roles, links, and ids inside it. `snapshotBoundary` and `compareSnapshots`, in `@portfolio/variant-contract/node`, do the comparing.

Desktop and mobile each take a screenshot of the whole page once every image on it has loaded or failed, lazy ones made eager first, attached to the report in `reports/variants/html/`. CI compares them against the baselines in `tests/variants/__screenshots__/`, pixel for pixel, and only in the pinned Playwright image (`PORTFOLIO_SCREENSHOTS=compare`) and for the platform's own `@portfolio/*` packages; a third-party variant gets the assertions alone. #11 sets the thresholds. Baselines come from CI's own run, not from a local one: when one is missing, the variants job writes it, fails, and uploads `tests/variants/__screenshots__/` as its shard's `variants-screenshots-1` or `variants-screenshots-2` artifact, and the new file is committed from there. A change that moves a first-party screenshot deletes its baseline and commits the one that run writes.

The `distinct` project checks that the first-party compositions really differ (`tests/variants/distinct.spec.ts`). It renders each one's home page on `complete` in one appearance, the platform defaults in light, with motion reduced and `Math.random` seeded, at 1440x900 and 390x844, and scores every pair three ways (`tests/variants/distinct.ts`). Structure is the boundary's tags and roles, with generic `div`s and `span`s dropped, as shingles of each element's last three path steps plus the landmark skeleton at four times the weight, compared by weighted Jaccard. Layout boxes are the top-level blocks across the first two viewports (landmarks, sections, articles, figures, media, `h1` and `h2`), matched greedily by overlap and compared as an area-weighted IoU. They leave out the `main` landmark, by tag or by `role="main"`: it wraps the blocks rather than being one, every composition's is full width and runs past both viewports, so any two pages' mains match almost exactly, and as the largest box it carried 0.4 to 0.5 of every pair's score whatever the pages drew. Structure still counts it in the landmark skeleton. Pixels are the first viewport's Sobel edges on a coarse grid, compared as 1 minus SSIM. The two design guards, structure and boxes, pass a pair at or under `T_dom` and `T_box`; a composition whose `quality/units/<id>.ts` exports `distinct: 'pending'` waits for its redesign, so a pair of two pending ones is reported, not failed, and a pending one that already passes against every other fails as stale until its lane removes the line. The pixel guard catches clones, not design: it fails any pair, pending or not, whose distance is under `T_px`, twice the noise a re-render, a dark scheme, or another typography makes. The thresholds, and every control with its role in each guard (`same`, `different`, or `informational`), are in `tests/variants/distinct.json`. `PORTFOLIO_DISTINCT_CALIBRATE=1 pnpm test:variants --project distinct-calibration` measures them again, on a fixture host with the route fixtures and the reference variant linked in and the static layouts in `tests/fixtures/variants/static-layouts/`, and writes `reports/variants/distinct/distinct.calibrated.json`. `pnpm test:variants-plan` unit-tests the arithmetic.

The `pack-distinct` project checks that the packs on one appearance axis really differ, design languages by default (`tests/variants/pack-distinct.spec.ts`). It renders one composition, the one `tests/variants/languages-distinct.json` names, under every selectable pack the build registers on the axis, the other axes at the platform defaults, with motion reduced and `Math.random` seeded, at 1440x900 and 390x844. It reads the packs from the registry at run time, so a merged or retired pack, which only an alias still names, drops out with no edit. Every pair gets two scores (`tests/variants/pack-distinct.ts`). Pixels are the first viewport's edges, read exactly as the distinct guard reads them. Tokens are a distance over the pack's token vector, with every token scaled to 0..1 by its grammar's range: lengths on a log scale up to the grammar's cap (64px, or 999px for a radius), bounded numbers linearly over their bounds, durations on a log scale up to 2s, and keywords as a match or not. For a design language, only the groups a static render shows score: corners, depth, borders and density. The material (surface) scores too, but only when the composition's first viewport shows a visible Surface primitive (`[data-ui-slot='surface']`) over 2% of it at both viewports. The run detects that from the page, `PORTFOLIO_PACK_DISTINCT_MATERIAL=on` or `off` overrides it, and the report's `material.json` records the result and why. Tokens average within their group, and the scored groups average with equal weight. Focus, motion, states, icons, texture and an unrendered material are informational lines for each pair, in the ranked list and a matrix each. They never enter the score, so a difference a still can't show never buys a pass. A pair fails when its pixels are under their alike line, whatever its tokens say, or when either score is under its clone floor. The token alike line decides only while the pixels have none. With `enforced` false, the run reports failures and fails only on a broken input. The report in `reports/variants/pack-distinct/<axis>/` has the pair matrices at each viewport, the ranked list, and the specimen sheets. For the design languages it also renders Editorial Evidence under every language after the verdict, for the report only, into `report-only/editorial-evidence/`: its pixel and informational matrices, its scores from the nearest pixels up, and its tiles and specimen sheets, so the owner sees each language on his own composition. Those scores never vote and never gate, since the verdict reads the scored composition's shots alone (`scoreShots()`), and a report-only render that fails is an annotation, not a failure. `PORTFOLIO_PACK_DISTINCT_CALIBRATE=1 pnpm test:variants --project pack-distinct-calibration` picks the composition whose first viewport the axis's tokens paint most: each visible element's share of the viewport times the distinct tokens its rules reach, motion tokens left out, at the viewport where that's lower. An axis's JSON can pin its composition with `pinned: true`, and the design languages' pins Spatial Bento: a composition registered later with more coverage never moves the scored one, and the calibration records the procedure's own pick and coverage in `procedurePick`, which the guard's report prints beside the scored composition (`composition.txt`). It then sets the thresholds from controls by the distinct guard's procedure. The "same" controls are each pack re-rendered, and the pack under another scheme and another typography. Another typography reflows the text, which the edge measure reads as another page, so it sets only the token score's floor, and the pixel floor comes from the re-render and the scheme. The "different" controls are, for each pair of families, the median cross pair of each score. The nearest cross pair would be a poor control, because two families can hold the same pack. `PORTFOLIO_PACK_DISTINCT_AXIS=colorScheme` or `typography` points both projects at another axis, with that axis's own controls and JSON.

On the other two axes the guard enforces (the LANG-5 enforcement commit): `tests/variants/schemes-distinct.json` and `tests/variants/typography-distinct.json` set `enforced` true and pin Spatial Bento, as the design languages' JSON does, and the design languages stay report only until LANG-5c. CI runs them in the variants job, one axis a shard (`pnpm ci:pack-distinct-schemes` on the first, `pnpm ci:pack-distinct-type` on the second), after the shard's own suite. A typography is scored as a language is, on its edges and its type tokens (each role's face, size, weight, line height and tracking). Another typography reflows the text, so the edges move for any two typographies, however alike their faces, and the edge score reads apart more often than the eye does. The report says so beside its numbers. A color scheme drops the edges, since they read luminance structure that a recolor barely moves. In their place it scores CIEDE2000 (`tests/variants/ciede2000.ts`, checked against Sharma, Wu and Dalal's 34 reference pairs) over seven roles: the canvas, the primary and secondary text, the accent, and the default, subtle and raised (`surface-prominent`) surfaces, in each base mode. Each mode's ΔE00 values combine as their mean, and the worse mode's mean over 50 is the score, so a pair that's a twin in one mode fails whatever the other does (before the LANG-5b fix round one mean over both modes let a dark-only twin pass). The score sits in 0..1 like every other and calibrate()'s gap of 0.1 is a ΔE00 of 5 (over 100 the nearest family pair, at 7.5, never cleared it), and any role under a ΔE00 of 2 is flagged as near, which never votes. The ΔE00 scale of 50 was chosen so the controls' gap can vote (over 100 the nearest family pair, at a mean ΔE00 of 7.5, never cleared calibrate()'s 0.1), and the calibrated line, alike under a mean ΔE00 of 3.8, is the decision (lead A, LANG-4). Generator schemes (brand-seed, hct-tonal and portfolio-artwork) are unscorable without the owner's input: every matrix and ranked list names them as such, and none is ever counted as distinct. A pack the build leaves out, such as profile-image, is named the same way. ΔE00 takes the edges' place in the fail rule: it decides whenever it votes, and the tokens decide only when it doesn't. Each scheme also renders in the dark display mode, and the colors both modes compute on the page are what score, its token vector included. A generator scheme registers no sets and solves its colors from the site's seed, and a scheme with one base mode renders that mode under either preference. A scheme's "same" controls compare the colors it computes under another language and another typography with its own, light against light. Its report adds `colors.json` (what each scheme rendered, and any role that drifts from its registered set), the ΔE00 matrices, the per-role ΔE00 for every pair in the ranked list, and light and dark tiles side by side. On every axis, `alike-<viewport>.png` shows every failing pair side by side, each tile named.

An enforced axis reads its JSON's `rulings` as distinct reads its acceptances. A failing pair passes only while a ruling names it, a clone never does, and a ruling whose pair fails nowhere is unneeded and fails the run, so the list can't outlive what it rules; a ruling with no pairs records a pack's standing and rules nothing. A scored role the render computes with an alpha under 1 is a problem that fails the run rather than a score, since the hex the guard reads would drop the alpha. Beside each scheme pair's token score, the report prints a painted score for every pair under 5 (`painted-under-5.txt`, and the ranked list): each role's ΔE00 weighted by the area Spatial Bento or Editorial Evidence paints it at 1440 (`PAINTED_WEIGHTS`, measured on every anchor scheme's captures), in each mode. It never votes. `pnpm report:derived-bound [ref]` lists, for each scheme whose anchors differ from `ref`'s (`HEAD~1` by default), every derived role that moved while its own anchor stayed, against lead A's bound of 2.0 ΔE00 with the hue within 5°; it reports only.

## The quality gates

The variant specs check a variant's contract. #11's quality cells check that it stays usable: every registered composition and surface, through axe at WCAG 2.2 AA and the keyboard, focus, occlusion, overlay, hover, reflow, content, enhancement, motion, transparency, and contrast checks, in each viewport and preference row the plan gives it, against a host built with the tier fixture packs.

```sh
pnpm exec playwright install chromium               # once
pnpm quality:pr                                     # the PR set, as CI's quality-pr job runs it
QUALITY_CHANGED_BASE=origin/main pnpm quality:pr    # plus the cells your changes since the merge base direct
pnpm quality:checklist -- my-id                     # the manual checklist for your composition
```

A change under your variant's package runs it against every stable design language (the owner's [37] rule), at every viewport in the default row and in every row at 1440x900, and a change to a pack runs it against every registered variant in the pack sweep, in the rule's five checks at 1440x900. Those cells' failure records name the changed axis, and their messages name the tokens the page's presentation boundaries resolved, with the `resolved-tokens.json` that keeps every one. The complete matrix, `pnpm quality:full`, runs a slice a night, every cell once a cycle, and `pnpm quality:release` runs it whole for a release candidate. [CONTRIBUTING.md](../CONTRIBUTING.md#the-quality-cells) has every command and option, and how manual runs are recorded in `quality/manual-runs/`.

The content sweep checks that a composition shows what the owner wrote (`apps/web/src/server/content-sweep.test.tsx`, in `pnpm test`). For the bundled sample and every contract fixture, it collects each authored string in the view: the words in every record and section, such as titles, captions, authors, tracks, and a testimonial's source, but never an id, URL, date, or enum. Then it renders every visitor route of every registered composition statically, as the network-off render does: home, each work's own page, and each path view. A string the fallback composition shows on its pages and a composition shows on none of its own is that composition's drop. Text matches as Flux's content test matches it: the visible text plus the alt, aria-label, and title attributes, Markdown reduced to its words, in lower case, without whitespace or punctuation. A string over 80 characters matches by its first 50 and its last 30, so a cut still shows. What a composition leaves out on purpose goes in its quality unit as `contentRuled`, a list of `{ field, reason }` entries. The field is a pattern over a drop's field, such as `work(music).tracks.title` or `section(hero).greeting`, where `*` matches within one step and `**` across steps. Every entry gives its reason in a sentence, and the sweep and the quality plan both fail an entry without one. For now the sweep only reports. It prints each composition's total, unruled, and ruled drops and its top fields, and it writes every drop to `reports/content-sweep/content-sweep.json`. Each count comes two ways. One counts every dropped string. The other, `unique`, counts each field once per pair, so the `large` fixture's hundred works dropping one field count once. `perFixture` gives both counts for each pair. The flip rule applies from the sweep's merge on: a composition's `COMPOSITION_STATUS` line flips to `ready` only with 0 unruled drops. Once the test's `ENFORCE` is true, the sweep fails any ready composition with an unruled drop, and any ruling that matches no drop. A pending composition is still only reported. `PORTFOLIO_CONTENT_SWEEP=enforce pnpm --filter @portfolio/web test` runs it that way before a flip.

## A variant from outside this repository

A variant published on its own ships in this format, which [`tests/external-variant/`](../tests/external-variant/) follows:

- Compiled ESM, its `.d.ts`, `styles.css`, and `manifest.json`. No TypeScript source, no install script, and no file for the host's `public/`.
- `"portfolio": { "kind": "variant", "manifest": "./manifest.json" }` in `package.json`, and exports `.`, `./manifest`, `./styles.css`, `./package.json`, and one subpath per declared enhancement, such as `./enhancements/badge`.
- Peer dependencies on `react`, `react-dom`, `@portfolio/schema`, `@portfolio/variant-contract`, and `@portfolio/kit` (#19 adds `@portfolio/appearance`), so it renders with the host's copies.
- An id that starts with its npm scope: `@acme/reference` is `acme-reference`.

An enhancement module is a client module (`'use client'`) whose default export takes `{ input }`. Only the host's browser registry names it, through its own `import()`, so its chunk loads once a page that renders `<Enhancement id>` has hydrated, never with the page.

Install one with `pnpm --filter @portfolio/web add <package or tarball>` and remove it with `pnpm --filter @portfolio/web remove <package>`. Neither changes anything but `apps/web/package.json` and `pnpm-lock.yaml`. A site that still selects a removed variant renders the fallback composition, with `variant.unavailable`, until the owner selects another.

Install only compositions you trust. A registered composition's code runs wherever it renders, Demo Studio's local frame under `demo` among them, which renders a visitor's own imported documents (#9). That frame's policy holds the composition to no `fetch`, socket, beacon, remote image, or `ping`, but not to a `<link rel=prefetch>`, which Chromium governs by no CSP directive, nor to DNS prefetch, `preconnect`, or WebRTC: a composition could use those to send what it renders to another host. Imported content can't add any of them, since its Markdown renders through the post-pass's allowlist and no field renders as HTML; the residual is the composition's own code, and the threat model's preview-7 row records it.

A content extension package sets `"portfolio": { "kind": "content-extension" }` and default-exports its `defineContentExtension(...)` result from `.`, with its renderers, if any, in `./renderers`. Every page loads `./renderers` in the browser too, so it must be client-safe: a server-only import there breaks `next build`. See [configuration.md](configuration.md).

`pnpm test:external-variant` checks the format end to end, without touching the checkout. It makes a temporary `git worktree` of HEAD, so commit first, and installs it from this checkout's pnpm store; the add and the remove may read package metadata from the registry, which a frozen install never needs. It builds `tests/external-variant/` (`@acme/reference`: evidence rendered bespoke as a ledger, fun facts unsupported, a recommended works slot, a `colophon` path view, a `compact` boolean control, and a `badge` enhancement), packs it, and adds the tarball, after which `git status` shows the dependency and the lockfile alone. After `pnpm build`, registry generation lists it and `check:variants` audits it; the compatibility test runs every registered composition on every contract fixture, and `pnpm config:validate` reports what the manifest earns (`kind.unsupported`, `slot.recommended-empty`, and `direction.unsupported`); the variant specs run for it alone; and its own checks cover the view, the control, and the enhancement's lazy load. Then it removes the package, after which `git status` is clean, rebuilds, and checks that a site selecting it gets the fallback composition, `variant.unavailable`, and degraded readiness. It needs `pnpm install` and Chromium, not a build of the checkout.

## The fallback composition

`packages/fallback-composition` is the host's stand-in and the clone source: every visible section in content order through the kit's shared renderers, in one column. Its header holds the name, at most five destinations from `navigationModel`, and the visitor control slot, with a `NavigationMenuSlot` in place of the destinations on a narrow screen. Its footer is the index, every titled section under its destination as real links, then one closing block that merges the contact section with the call to action beside it: one heading, one message, the actions with the address beside them, and the other ways in last. A case study ends on a short index of the destinations and the works. It's the reference for using the navigation model, the Menu slot, and `footerOutline().cta`; your own chrome, index, and closing form look nothing like it. It's `document`, `still`, and `light`, with empty `renderedKinds` and no slots or controls. It renders for a selection no package registers, and for the contract fixtures; a site can't select it. Fixtures select `missing-variant`, an id no package may take, to reach it.

## Visual companion

The variant-developer skill ships a visual companion at `skills/variant-developer/scripts/visual-companion/`:

- **Mockup mode** (an HTTP server and a file watcher) for layout boards and section sketches before code exists.
- **Preview mode** runs the dev server and polls the dev fixture route, `/preview/dev/<id>/<fixture>`, until it answers 200. The route renders one of the contract fixtures (`complete` unless you pass `--fixture <name>`) in the variant, in the preview document and under the preview's headers, the way Studio's preview frame will (#7). `?displayMode=`, `?contrast=more`, `?motion=reduce`, and `?enhancement=off` set its environment, and any other value is a 404. Only `next dev` serves the route: a production build answers it as a path no route matches. The dev server runs under `PORTFOLIO_PROFILE=demo`, so `/sample?variant=<id>` shows the bundled sample too.

```sh
bash skills/variant-developer/scripts/visual-companion/start.sh
bash skills/variant-developer/scripts/visual-companion/start.sh --mode preview --variant <id> [--fixture <name>]
bash skills/variant-developer/scripts/visual-companion/start.sh --mode preview --variant <id> --matrix
```

For screenshots, run the variant specs, as in [Testing a variant](#testing-a-variant); `--matrix` runs them for the one variant.
