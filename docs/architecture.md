# Architecture

How the pieces fit together.

## One-paragraph overview

An open-source portfolio platform configured by two documents and its environment. `portfolio.yml` holds the content, `site.yml` holds the presentation and product behavior, and the environment holds the deployment settings and secrets. At startup the Next.js host in `apps/web` checks its deployment settings, reads both documents once, validates them as a pair against `@portfolio/schema` and the variant contract, and renders the portfolio's public view through the site's variant: a composition package registered as a dependency of `@portfolio/web`, or the fallback composition when the selected one isn't. Variants are independent React packages that arrange the content, through `@portfolio/kit`'s shared section renderers or their own; color, type, and display modes are the appearance system's (#19). Under `owner`, the documents are import input, and a revision store in the data directory holds what's published ([Storage](#storage)). [configuration.md](configuration.md) documents both documents.

## Data flow

```
┌───────────────────┐
│  config/          │  The portfolio document and the site
│   portfolio.yml   │  document, and beside them the unit's
│   site.yml        │  derived data: snapshots/<kind>.json
│   snapshots/      │  and, from #10's slice 2, media/
└─────────┬─────────┘
          │ read once at startup by the documents adapter (CatalogReader)
          ▼
┌───────────────────┐
│  @portfolio/      │  loadPair: find, read, parse, validate the pair
│   schema          │  readUnitFiles: the snapshots and media document
│                   │  resolvePortfolioView: the published view
└─────────┬─────────┘
          │
          ▼
┌───────────────────┐
│  apps/web         │  buildRenderInput, then the document boundary
│   page.tsx        │  resolveAppearance() decides, with its skip
│   layout.tsx      │  link; layout.tsx sets <html lang dir> alone
└─────────┬─────────┘
          │
          ▼
┌───────────────────┐     ┌──────────────────┐
│  a registered     │ ──> │  packages/kit    │
│   variant, or the │     │  (sections,      │
│   fallback        │     │   enhancements,  │
│   composition     │     │   motion, SEO)   │
└─────────┬─────────┘     └──────────────────┘
          │
          ▼
       Browser
```

## Layers

### `@portfolio/schema`

The contract. Its entry points:

- **`@portfolio/schema`**: the schemas and the pure, browser-safe functions on them.
  - `PortfolioSchema` at `schemaVersion: 3` and `SiteSchema` at `schemaVersion: 2` (`SCHEMA_VERSIONS`). `composeSchemas(extensions)` builds them for a set of content extensions, and `DEFAULT_SCHEMAS` is the set for none. Every object is strict, and any object may carry namespaced `extensions`.
  - The version 3 model (#10): works, evidence, chronology entries, and media assets are records with document-unique ids; the practice and the contact record sit beside them; `signature`, `featured`, `proof`, and `archive` curate them; and the sections list them in reading order. The section union is 14 core kinds discriminated by `kind`, plus `<package name>/<name>` kinds from content extensions. `CORE_SECTION_KINDS` lists the core kinds for the variant contract and the skill drift gates.
  - `parseSource` reads YAML or JSON within the document limits and locates every pointer by line and column. `validatePublicationUnit(unit, ctx)` takes both documents, checks each alone and then the pair against an appearance catalog, the registered extensions, and the canonical origin, and returns `Diagnostic` records. `resolvePortfolioView(pair, unit, { mediaBase, extensions })` makes the published view, the only input visitors' output is built from: it drops hidden sections, private records, every record and asset nothing visible reaches, and unregistered extension data, resolves references, and wraps each derived value, a media asset's renditions or a github section's snapshot, as ready with when it was derived, or unavailable with why. It's pure: no file, no network, no clock.
  - `defineContentExtension`, `applyEdits`, `serialize`, `canonicalize`, `detectDocument`, the URL allowlist, and the secret scan.
- **`@portfolio/schema/node`**: `findPair`, `readPair`, `loadPair`, and `formatRecords`, which read a directory or two files from disk, and `readUnitFiles`, which reads the unit's `snapshots/<kind>.json` and `media/media.json` beside them. It's Node only, and `pnpm check:deps` keeps it to server code, the config command, and tests.
- **`@portfolio/schema/migrate`**: the one-time migration from the old one-file format, which only `pnpm config:migrate` and its tests import.
- **`@portfolio/schema/ids`**: the section id and extension kind rules, free of zod so the kit and the variants can use them.

The schema is the only source of truth. If a doc disagrees, the schema wins.

### `@portfolio/kit`

Things every variant needs but shouldn't reimplement:

- **`@portfolio/kit/sections`**: `renderSection`, the shared, accessible renderer of every core kind, which a variant uses for each kind it doesn't render bespoke, and which renders nothing for a section with nothing public; the pieces they're built from, `WorkEntry`, `EvidenceEntry`, `MediaFigure`, and `CaseStudy`, with the view helpers that find a section's records and a placement's image (`worksOf`, `placedImage`, `placedMedia`, and the rest); `RichText`, the one markdown path; `seededRandom`; `VisitorControlSlot`; and `registerHostModules`, through which the host hands the kit the registered extension renderers and enhancement loaders. Every text node they render is the owner's, formatted from the owner's data, a snapshot's value with its date, or one of the fixed labels #10 lists.
- **`@portfolio/kit/enhancements`**: `Enhancement`, the client component that loads a variant's declared enhancement in the browser after the page is readable, and renders nothing if it fails; and `EnhancementIsland` (#6), which renders the variant's server markup, loads the enhancement only once its runtime is active and the browser meets its `requires`, keeps it loaded through a pause, and tears down to that markup if the chunk or the enhancement fails.
- **`@portfolio/kit/runtime`** (#6): the one runtime every kit effect and enhancement runs on. `useEnhancementRuntime` resolves an effect's state from the document and its root: static until the page has mounted, under reduced motion (the OS, the site's `reduce` policy, or a preview environment's `data-motion="reduced"`, and the stricter always wins), and after a failure; paused while a preview frame is hidden or out of focus, as #7's frame agent says with its `kgn-preview-lifecycle` event, while the document is hidden, while its root is offscreen, or while the visitor paused motion; active otherwise. A root that isn't active carries `data-activity="paused"`, which `experience-base.css` turns into `animation-play-state: paused` for CSS animations below it. `useFrameLoop` runs a `requestAnimationFrame` loop only while its runtime is active, and is the kit's only frame loop. `MotionControl` is the visitor's pause: a pressed button with a polite status, kept for the tab in `sessionStorage`, disabled and saying so under the OS's reduced motion, and absent under the site's `reduce` policy. Every spatial, spatial-r3f, motion-fx, typing, and counter effect runs on it; a SpatialCanvas renders frames continuously only while it's active, and gives its scene `useSceneAnimates`.
- **`MotionPolicyProvider`** and **`useMotionPreference`**: the site's motion policy for every component below them. A component's own policy can only add a reduce. It says `reduce` on the server and while hydrating, before the OS's preference is known, which then comes from the runtime's store, and the runtime reads the provider's policy too.
- **`fetchGitHubData`**: the server-side GitHub fetcher, which no render uses: a github section renders its snapshot. #10's third slice moves it behind the snapshot adapter, and the variant audit refuses it.
- **`format.ts`**: `formatDate`, `formatPeriod`, `formatDuration`, `formatRelativeTime`, `formatCompactNumber`, `formatList`, `slugify`, and more.
- **`buildStructuredData`**, **`renderRssFeed`**, and **`deriveNavItems`**: JSON-LD, the feed, and the navigation from the published view, each record's `@id`, GUID, and anchor made from its id.
- **Pretext, spatial, spatial-r3f, motion-fx, and markdown**: opt-in submodules for variants that need them.

### `@portfolio/variant-contract`

The variant contract, version 2.0: the manifest's schema and `validateManifest`; `buildRenderInput`, which builds the one `VariantRenderInput` a variant renders from, the same way on the server, in #7's preview frame, and in #9's browser render; controls and their migrations, with `planControlsMigration`, which `pnpm variants:migrate-controls` applies; route helpers; and `compatibilityFor`, the report of how a pair renders in its composition, which `contractValidators` hands to `validatePublicationUnit` as one unit validator. Live, as startup runs it, a finding only warns when something renders in its place. `@portfolio/variant-contract/node` reads the host's dependencies into a registry, #19's packs through the pack checks the host passes it, writes the generated modules and the packs' compiled files, and audits variant source.

### `@portfolio/appearance`

The appearance axes (#19): token contract 1, the `--color-*`, `--ui-*`, and `--type-*` properties packs define; the strict manifests of design-language, color-scheme, and typography packs, with `validatePackManifest`; `createAppearanceRegistry`, over the generated metadata module; `resolveAppearance`, what a boundary renders for the published selection, the visitor's cookie or demo query, the profile, and the environment; `setAxis`, `serializeSelection`, and `parseSelection`; `resolveTokens`, typed values for server code; `validateAppearance`, the unit validator that takes over from the appearance catalog; and the appearance part of the `legacy.document` remediation. Its root entry is browser-safe. `@portfolio/appearance/node` compiles a pack into one stylesheet inside its cascade layer, each starting with `LAYER_ORDER`, builds the platform stylesheet (the `reset`, `utilities`, and `accessibility` layers), and runs the contrast gate; `@portfolio/appearance/generators` holds the browser-safe scheme generators. The fallback packs are workspace packages: `platform-neutral` in `@portfolio/appearance-languages`, `warm-parchment` in `@portfolio/appearance-schemes`, and `humanist-ui` in `@portfolio/appearance-typography`. The test fixture packs are in `packages/appearance-fixtures-*`. The host renders every page with it (#19, Slice 4): `lib/document-appearance.ts` resolves the page's boundary and links the platform stylesheet and the selected packs', and startup and publish check the site's appearance against the registries (`lib/appearance-checks.ts`).

### Variants

A variant is an isolated package, a dependency of `@portfolio/web`:

- **`manifest.json`**: contract 2.0. The id, the one-sentence promise, the composition family, the motion intent, the performance tier, the kinds it renders bespoke or skips, its routes, controls, content slots, enhancements, text directions, and provenance.
- **The `.` export**: the default component, which takes `{ input: VariantRenderInput }` and renders one `<main id={input.ids.main}>` and one `VisitorControlSlot`, synchronously, from the input alone.
- **The `./styles.css` export**: layout only, every selector under `[data-variant='<id>']`. Registry generation compiles it with the kit's shared renderers' layout first, all of it inside #19's `variant-layout` cascade layer after the layer-order statement, and copies the images its `url()`s name by content hash. The page that renders the variant links it, and no other page does.
- **`"sideEffects": false`** in its `package.json`, as the kit and the shared packages declare it, so a page's chunks keep only the modules it uses.

`packages/fallback-composition` stands in for an unregistered selection: every section in content order through the shared renderers. `packages/variant-kinetic-cosmos` is the first composition (#14): an orbital opening, evidence that opens in place, and a chronology in its authored lanes. The retired v1 Editorial package sits in `legacy/`, outside the workspace, for #13 to rebuild. Variants must not reach into other variants, and talk to the host only through the manifest and the render input. [variants.md](variants.md) covers building one.

### `apps/web`

The Next.js host. Responsibilities:

- **Startup**: `src/instrumentation.ts` validates the deployment settings (`src/server/config.ts`, the only code that reads them) and composes the profile before the server takes a request. The `documents.pair` startup requirement reports the pair's records, so the pair is checked once: a blocking record logs a `config.fatal` line and stops the process, and a warning logs a `config.warning` line.
- **`getLive()`**: `src/server/catalog.ts`, the one way pages and metadata routes read the pair. Under `owner` it's the live revision in `PORTFOLIO_DATA_DIR`, which `@portfolio/core`'s `RevisionCatalogReader` serves, or the last known good while that one can't be served; until the store has published, it's the mounted pair. Under `read-only` it's the frozen revision the source adapter (`server/catalog-source.ts`) loaded from `PORTFOLIO_SOURCE_DIR`, and owner's mounted pair is read the same way; under `next dev` the adapter checks the pair again after each edit. Under `demo` it's the bundled sample pair (`server/catalog-sample.ts`), which never reads a source directory.
- **Public view**: `server/public-view.ts` turns the live unit into the published view, with renditions under `/media`. It's the only input to the page, its metadata and JSON-LD, the feed, and the Open Graph image. Both catalog adapters read the unit's snapshots beside the pair, and a snapshot that doesn't read stops startup with a named record (`snapshot.syntax`, `snapshot.invalid`).
- **Appearance checks**: `lib/appearance-registry.ts` builds the registry of the packs and variants this build registers, and `lib/appearance-checks.ts` checks a pair's appearance against it, every id and display mode, as `validateAppearance()` does: live, a pack this build lacks warns and its axis falls back, and a publish blocks it. A legacy document's remediation names the registered ids. The contract's validators check the variant (`lib/variants.ts`'s `liveContext()`).
- **Capabilities**: `src/server/capabilities.ts` is the profile matrix: what `owner`, `demo`, and `read-only` may do, as data. `CapabilityPolicy` (`server/policy.ts`) answers from it and builds the server-side navigation.
- **Route table**: `server/routes.ts` maps every route file to a capability. Pages and metadata routes export `servedPage('<pattern>', render)` as their default, and route handlers export each method as `served('<pattern>', handler)`, so a profile that doesn't serve the route gets a 404. `pnpm test` maps every app file to its URL with Next's own helpers and fails on a route file without an entry, on any other export, on a route directory outside `src/app`, and on any `'use server'` directive; the browser suite checks the build's route manifests against the table. `src/proxy.ts` answers 404 early for routes the profile doesn't serve, gives each request a fresh `x-request-id`, and marks a path no route renders as missing.
- **Operations**: Studio queries and commands are entries in `server/operations.ts`, the revision store's with their schemas in `server/store-schemas.ts`, run only through `/api/studio/[name]`. Its dispatcher checks the profile, the session, the origin, the capability, and the input, in that order, under the policy of the stored deployment. The auth provider supplies the session, origin, session-slide, and throttle steps; a handler answers with its output or a `StudioResult` (a status and headers, a 303, or an error from `ERRORS` it declares). The store makes its own version checks under the publication lock, so `draft_conflict` and `live_conflict` come from the handler, and an owner session's 409 or 422 carries the payload in `error.details`, checked against the entry's schema. Every other error body, a 5xx above all, is the fixed one.
- **Composition**: `server/composition.ts` builds what the profile needs and runs the named startup requirements. It's the only module that imports `server/owner/`, and only through `import()`: `pnpm check:deps` fails any other importer and any static import from the root itself. Auth providers register as factories that load in the owner branch, owner requirements can load their checks from owner code, and a failing `degraded` requirement starts the server and lists itself in `DeploymentState.degraded`.
- **Logs**: `server/log.ts` writes one JSON object per line on stdout, with allowlisted fields only. Startup logs the redacted `deployment.config` summary once, and `onRequestError` in `src/instrumentation.ts` logs each request error's digest with its request ID.
- **Health and readiness**: `/api/health` is liveness and does no I/O. `/api/ready` reports `server/readiness.ts`'s checks: the catalog, the site's variant (`packs`, `degraded` while the fallback composition renders in place of an unregistered one), and, outside `owner`, that no owner module has loaded.
- **Headers**: `next.config.ts` sets `X-Content-Type-Options`, `Referrer-Policy`, and `Content-Security-Policy: frame-ancestors 'none'` on every route but the preview's, and `Access-Control-Allow-Origin: *` on `/_next/static/*` and `/_portfolio/*` alone, which a sandboxed preview frame loads cross-origin. `src/proxy.ts` sends the public site's own policy in place of that one on every other response (`server/public-headers.ts`, #6): a nonce made per response with `strict-dynamic`, which it puts on the request too, so Next puts it on every script it renders. It sends Studio's own policy, and under `/preview` and `/preview-assets` the preview's (`server/preview-headers.ts`): a CSP with a nonce made per response, `X-Robots-Tag: noindex, nofollow`, `Referrer-Policy: no-referrer`, and `Cache-Control: private, no-store`, on every response there, 404s included, and it passes those requests on without their cookies. It answers anything under the two shared prefixes that isn't a GET or HEAD of a file Next serves there, a build asset, or exactly a file registry generation wrote into `public/_portfolio/` (`server/portfolio-files.ts`) such as a compiled pack, spelled as Next serves it, or a route the table serves, with the plain 404. A build asset that doesn't exist still gets the views catch-all's 404.
- **Variant registry**: `scripts/build-registry.ts` reads `@portfolio/web`'s direct dependencies, checks every variant, content extension, and appearance pack among them, and writes the gitignored `src/lib/generated/` modules: the metadata module, `registry.meta.ts`, which is `server-only` (#6): the manifests, the packs with their compiled files, and `ASSET_MANIFEST`, what each unit ships to the browser, its stylesheet with its bytes, gzip bytes, and hash, its fonts, images, stills, and enhancements; a loader per variant; the extensions' definitions and, in a module of their own, their renderers; the enhancements; and the packages `next.config.ts` transpiles. Node tools read `asset-manifest.json` and `trace-matrix.json` beside them in place of the metadata module. Each pack's stylesheet, and the platform stylesheet, go by content hash into the gitignored `public/_portfolio/pack/`, the fonts a typography profile ships into `public/_portfolio/font/` (#6), each `@font-face` with its declared `unicode-range` and `font-display: swap`, and each role's stack ending in its fallbacks, each variant's compiled stylesheet into `public/_portfolio/variant/`, the images those name into `public/_portfolio/asset/`, and each variant's committed stills, the catalog's first paint of it, into `public/_portfolio/still/`, which hold only what the build registers. It writes each variant's experience segment too, `app/(site)/%5Fexperience/<id>/` (Routing, below). `typecheck`, `test`, `check:variants`, `check:deps`, the `config:*` scripts, and the CI scripts that load the route table run it with `--modules-only`, which leaves `public/` alone. A write stages each file in the gitignored `apps/web/.cache/portfolio-served/`, outside `public/`, and renames it into place, so a copy of `public/` never meets a half-written or vanishing file, and it removes another run's staged file only once that run's process is gone. `scripts/registry-options.ts` passes the generator #19's pack validator and compiler, so `@portfolio/variant-contract` imports neither, and the fixture gate in `scripts/fixture-gate.ts`, a table from fixture package directories to the flags that admit them: a `portfolio.fixture: true` package registers only when its flag is set, such as `APPEARANCE_FIXTURES=1` for `packages/appearance-fixtures-*` and `PREVIEW_FIXTURES=1` for `packages/preview-fixtures`, generation fails on one no row maps and on an unmarked package in a directory a row maps, and a build without the flag fails if one of its ids registers another way. The metadata module's `FIXTURE_FLAGS` says which flags were set. `BUDGET_FIXTURES=1` admits #6's fixture variants `fixture-variant-light` and `fixture-variant-medium` and its typography profile `fixture-type-font`, which ships a font the trace publishes, in `packages/budget-fixtures/`, and `BUDGET_FIXTURES=over` admits `fixture-over-budget` alone. `predev`, `prebuild`, `typecheck`, `test`, and `check:variants` run it; installing doesn't. `lib/variants.ts` reads the manifests, the stylesheets' URLs, and the extensions, and loads no variant; `lib/variant-loaders.ts` holds every variant's loader, for what renders the variant a request names: #7's preview routes and the startup health check. `lib/host-modules.ts` registers the extension renderers with the kit on the server, and in the browser each experience segment's own client module registers them and that variant's enhancement loaders, and `lib/host-modules-client.tsx` every variant's, for the preview routes. Only the browser names the loaders: `<Enhancement>` loads nothing on the server, and a server module that imported an enhancement would make it a client reference the page loads at once, not after it hydrates. `pnpm check:deps` fails a host module other than these that imports a variant package, and anything in `app/(site)` that reaches every variant's loaders or enhancements.
- **Routing**: public pages sit in the `app/(site)` route group, under its own root layout. The route table lists the visitor pages: `/` and the views under it, `/[...view]`; `/work/[slug]` and `/work/[slug]/[...view]`, a work and its views, the 404 page until #10 resolves slugs; and under `demo`, `/sample/[[...path]]`, the same routes below `/sample`, in the sample's own selection or the registered variant `?variant=` names, which every link and redirect keeps, with every response marked `noindex`. None has a route file of its own: each renders in the experience segment of the composition it shows (#6, Slice 2), `app/(site)/%5Fexperience/<id>/[[...route]]/page.tsx`, which registry generation writes for each registered variant, the fallback composition's included, and which imports that variant and no other. Next serves a `%5F` folder at an underscore, so it's `/_experience/<id>`, a first segment the contract reserves. Once every check has let a GET or HEAD of a visitor page through, `src/proxy.ts` names its segment in `x-portfolio-experience`, the RSC and prefetch requests of Next's router included, from memory alone: `server/experience.ts`'s `segmentFor()` reads the live composition `config-store` holds, which the composition root's reader writes on every `getLive()`, whichever reader the profile has, and under `demo`, `/sample`'s `variant` parameter, checked against the registry. `next.config.ts` rewrites the request to `/_experience/<id>` and its path, with its query as sent, and only for a value that is an id whole. It's an afterFiles rewrite, which runs once Next has looked in `public/`. Among the beforeFiles rewrites it would also carry `/_not-found`, where the router prefetch rule sends a prefetch with no RSC header, on to a segment, since Next applies each one that matches to the path the one before it left. proxy.ts drops any copy of the header the client sent, and rewrites nothing itself: Next gives the proxy's request an origin of its own, which isn't always the one its router compares a rewrite with, and it fetches a rewrite to any other origin over the network. Any other method to a visitor page gets a plain 405 with `Allow: GET, HEAD`, and a request for an experience segment's own path, in any spelling and to any method, answers as a path no route matches. The segment's page, `server/experience-page.ts`, asks the route table about the path again, reads the live revision, and asks `segmentFor()` once more, which reads the value the reader just wrote: when the revision changed after the proxy read it, it answers a 307 to the same URL, and the next request lands in the right segment. Then it asks `lib/visitor-routes.ts` what the path is, and runs `dispatch()` against the composition that renders: a view of it renders, a path only another installed variant declares is a 307 to its parent route, and anything else is the 404 page. `ExperienceDocument` (`lib/experience-document.tsx`) renders the page, the same for a visitor and a preview: the document boundary `lib/document-appearance.ts` resolves, `<div data-appearance-boundary="document" data-variant ...>` with the packs, display mode, contrast, motion, and enhancement it renders, `data-requested-<axis>` where an axis falls back, such as the fallback composition standing in, and its skip link first; the visitor control's model for the variant's slot; and a path view's canonical link. `experienceHead` (`lib/experience-head.ts`) builds the head from the unit it renders: title, description, share metadata, and JSON-LD. `lib/experience-styles.ts` imports `app/experience-base.css`, the one host stylesheet a portfolio document loads, and the presentation boundary links the compiled stylesheet of the variant it renders, as a React stylesheet resource that React hoists into the head; `app/host-chrome.css` is for Studio's layout alone. The root catch-all leaves every first segment the route table owns, and `_next`, to its own route, and the contract reserves each, so no view is shadowed. While `isServable()` is false, `src/proxy.ts` answers visitor pages with a static 503. `app/(site)/not-found.tsx`, and `app/global-not-found.tsx` for a URL no route matches, render inside the live site's boundary, and `not-found.tsx` inside the boundary of the composition the request's experience segment renders, where that isn't the live site's, since Next puts it in every page's payload with the stylesheet its boundary links; they, `app/(site)/error.tsx`, and `app/global-error.tsx` show generic pages that never print error details. The route table also knows, from the build's manifests and never the live site, which paths name nothing: one no installed variant declares, a work until #10, a placeholder value over 64 characters, a first segment no route answers, or a `?variant=` that names nothing. `src/proxy.ts` sets `x-portfolio-route: missing` on such a request, in place of anything the client sent, and `next.config.ts` rewrites it to Next's `/_not-found` route, which renders the global 404 page from the server with its 404 status. A route spelled with a fixed segment percent-encoded, such as `/%66eed.xml`, answers the same way in every profile: the route table reads it decoded, but Next matches a fixed segment as sent and would hand it to the views catch-all, so `src/proxy.ts` marks a GET or HEAD for it `x-portfolio-not-found`, which `next.config.ts` sends to `/_not-found` before it looks anywhere else, and answers any other method with the plain 404. A missing path that is a route file's own, as sent or decoded whole, such as `/work/[slug]` or `/studio%2Fsign-in`, goes the same way, since Next's file check finds the file before the afterFiles rewrite runs. The rewrite runs after Next looks in `public/`, so a file there is still served, and `server/routes.test.ts` fails on a top-level `public/` name a view could take, and on any Compose mount into `public/`: images serve from `/media` alone. The one 404 that still draws in the browser is a view the live variant declares and the site document's `routes` turns off: Next 16 answers a page's `notFound()` with an error document the browser fills in, so without JavaScript that page is empty; the status is 404 either way.
- **Fixture pages**: `app/(fixtures)` is the test fixtures' route group, under a root layout that loads no host chrome. Its `%5Ffixtures/appearance/page.tsx` serves `/_fixtures/appearance` (#19): every shared primitive in each state, in a document boundary, and plates of other selections, which `tests/appearance` checks. Its capability, `appearance.fixtures`, follows the build's `FIXTURE_FLAGS`: every profile of a build made with `APPEARANCE_FIXTURES=1` serves it, and no profile of any other build does. The route table calls a route no profile of the build serves absent and unknown, and `src/proxy.ts` answers a GET or HEAD for it as a path no route matches, through the beforeFiles rewrite, and any other method with the plain 404. The catalog fixture, `/studio/_catalog-fixture` (#6, item 5), is a Studio page of the same kind: registry generation writes its route file, `app/(studio)/studio/%5Fcatalog-fixture/page.tsx`, only in a build made with `BUDGET_FIXTURES` (`scripts/fixture-routes.ts`), removes it in any other, and stops on one there it didn't write. Its capability, `catalog.fixtures`, is the owner's with a session in such a build alone, and `requireOwnerPage` checks it before the page reads anything; under `demo` and `read-only`, and in every other build, the path answers as any unknown Studio path does, and `pnpm check:standalone` fails a default build whose output holds its code. It shows a plate per registered variant, each the variant's committed still, and a live preview frame in its place only while `lib/studio/preview-scheduler.ts` says so: on the owner's request, or within a viewport of the screen, two frames at most and one of them `heavy`. A plate mounts its `PreviewSurface` while it's live and unmounts it once it isn't, and a requested frame scrolled offscreen goes `hidden` through #7's lifecycle. It's #8's and #9's catalog in miniature, for `tests/trace/catalog.spec.ts`.
- **`(site)/layout.tsx`**: sets `<html lang dir>` from the portfolio's `locale` and `direction`, renders no script of its own, imports `lib/experience-styles.ts`, which brings `app/experience-base.css`, and takes its metadata and JSON-LD from `experienceHead` on the live revision. `ExperienceDocument` renders the client module its caller hands it, which registers the host modules in the browser.
- **One route per variant** (#6, Slice 2, item 3): Turbopack gives every page one client chunk group, every client module its server graph reaches, and the browser loads the whole group for any client reference in it. With one route segment that could render any variant through the registry's loaders, every visitor downloaded every variant's client code: the trace of a `BUDGET_FIXTURES=1 PORTFOLIO_ANALYZE=1` build found one chunk holding `fixture-variant-medium`'s shader stage and visibility gate beside `fixture-variant-light`'s toggle and the kit's enhancement runtime, loaded on the light page, the medium page, and the fallback composition's alike. So each variant has a segment of its own, and the rewrite above sends each visitor page there. `pnpm test:trace` holds every public page to it (Experience purity, below).
- **Experience purity** (#6, Slice 2, item 6): `pnpm test:trace` loads each registered variant's home page under `owner` and `read-only`, and the pages it links to and a 404 page, and fails a page that downloads, or whose HTML and RSC payload name, anything but `app/experience-base.css` and the units it renders: a module from another unit's package, another unit's stylesheet or file from `ASSET_MANIFEST`, a module matching a glob in `runtime-budgets.json`'s `forbidden` block, such as Studio's and the preview's code, a third-party request, or a link to `/studio` or `/admin`. Modules are matched through the source maps a `PORTFOLIO_ANALYZE=1` build ships, so a chunk without one fails the page, and a glob that matches no file fails every page (`tests/harness/trace/purity.mjs`).
- **Cache keys and preloads** (#6, item 8): a unit file's URL is its cache key. Registry generation names every file it writes under `public/_portfolio/`, packs, fonts, variant stylesheets, assets, and stills, by the first 12 hex digits of its SHA-256, so a changed file gets a new URL and an unchanged one keeps its cached copy across deploys. `next.config.ts` sends `Cache-Control: public, max-age=31536000, immutable` on exactly those names, by `server/cache-rules.ts`'s pattern; anything else under `/_portfolio/`, a 404 included, keeps `no-store`, and documents, `/api`, `/preview*`, and Studio keep their own caching. A page links only the units it renders: its variant's stylesheet, as a React stylesheet resource, the images and fonts that stylesheet names, and, once #19's Slice 4 links them, its packs'. Nothing preloads or prefetches another unit's file, so switching one axis downloads that axis's unit and nothing else: the visitor's appearance control loads only the stylesheet the new choice needs, and the catalog's plates load a variant's files only once its frame is live. Stills are plain `<img>` elements with their width and height, the first eager and the rest lazy. `tests/trace/catalog.spec.ts` proves it for the variant axis: each plate's frame downloads its own variant's files, by `ASSET_MANIFEST`, and no other unit's.
- **Runtime budgets** (#6, items 3 and 4): every variant and appearance pack manifest may declare `budgets` in six kinds, JS, CSS, image, font, animation, and enhancement, and registry generation copies them into `ASSET_MANIFEST`. `runtime-budgets.json`'s `budgets` block sets a ceiling of each kind for each variant tier and each pack axis, with the calibration measurement it rests on; a kind a unit leaves out is its ceiling. `pnpm check:budgets` (`ci/check-budgets.mjs`, over `ci/lib/budgets.mjs`) reads `ASSET_MANIFEST`, the build output, and the trace report, and measures each unit on its own: a stylesheet's gzip bytes, its image and font files, a variant's own JavaScript through the trace's source-map attribution on each route, its worst case, the continuous work the trace's probes count, and each enhancement's chunks in the build. It writes `reports/budgets/budget-report.json` and one failure record per breach, each with the unit, metric, route, the asset that carries the most of it, the actual and the limit, and the command that rebuilds and traces it. Nothing sums units, routes, or kinds into one total. It also fails a declared budget over its ceiling, a unit with no ceiling row, a unit stylesheet with a remote `@import` or `url()`, a `/_portfolio/` file a traced page loaded that `ASSET_MANIFEST` omits, a variant no trace case renders, and an enhancement no chunk holds. CI's `trace` job (`pnpm ci:budgets`, `ci/budgets.mjs`) builds the budget fixtures with source maps and traces them: `BUDGET_FIXTURES=1` must pass, and `fixture-over-budget` must fail with one record for each of its JS, CSS, and remote `@import`.
- **Preview**: `app/(preview)` holds the preview routes (#7), apart from the site's and Studio's layouts. Each route's root layout renders `PreviewDocument` (`app/(preview)/document.tsx`): the previewed unit's language, direction, and JSON-LD, its page, which renders `ExperienceDocument`, and one agent (`src/preview/agent.tsx`) that renders nothing. Its metadata is the previewed unit's head with `noindex, nofollow`. Under `owner`, `/preview/[grant]/[[...route]]` renders a frame for a preview grant, and `/preview-assets/[grant]/[...path]` serves a rendition of the media the grant pinned (#10), `private, no-store`, through the port's `asset()`, and the status document for anything else. The grant service is `@portfolio/core`'s `preview/`: `token.ts` makes a grant's 128 random bits and names it by their SHA-256 digest, `grant-store.ts` keeps the records under `ephemeral/preview/` in the data directory, and `grants.ts` mints, checks, renews, revokes, and sweeps them. A grant is bound to the #2 session record it was minted under, by digest, and to the deployment's profile and Studio origin, and every request checks it again: its hash known, not expired, its session still counting, and for a draft, the draft still there and no newer version minted. #3's `published` and `draftDiscarded` events and #2's `onSessionEnded` only end grants sooner. `server/owner/preview.ts` wires the service into the owner composition: the `preview.grant.mint`, `preview.grant.renew`, `preview.grant.revoke`, and `preview.grant.status` commands, the store reads, and a `PreviewGrantsPort` (`server/preview-port.ts`) in the deployment state. `src/proxy.ts` is the per-request gate: a grant path goes on to Next only as a frame's document load, `Sec-Fetch-Dest: iframe`, or as an image, video, audio, track, or font load of an asset, for a grant the port admits, and every other request under the two prefixes gets one static status document (`src/preview/status.ts`). The page opens the grant again through the port, which builds `Authorized<'preview.grant'>` from the bound session, and renders the preview document with the grant's path as its link base and the view `resolvePortfolioView` builds, its renditions under `/preview-assets/<grant>`. The frame talks to Studio over the preview channel (Slice 3): `src/preview/protocol.ts` is every message as one zod schema both sides read with, with its size limits, `src/preview/frame-channel.ts` is the agent's half, and `src/preview/studio-channel.ts` is Studio's, with no UI, which Slice 4's `PreviewSurface` wraps. The layout renders the grant's channel nonce, Studio's origin, and the link base for the agent, which in a framed document says `hello` to Studio's origin after each load, and again four times over the next few seconds, and Studio answers its frame's own window, with that frame's nonce, with a `MessagePort`. Studio closes the port on every load of the frame, since it can't tell which document a load is for, and a later hello opens another. In the frame every move is a document load under the grant: the agent loads internal links and Studio's `navigate` there, and cancels every other link, clicked, middle-clicked, or clicked with a modifier key, which goes to Studio as `link`. Where the frame's document has an origin of its own, the Navigation API's `navigate` event backs that up for what a click doesn't show, such as a link in a closed shadow root, a script's own navigation, a reload, or a history change, and only back and forward go on unread. Under `owner`, `/studio/preview` (`app/(studio)/studio/preview/page.tsx`) offers the working draft and the live revision through the port's `previewable()`, and shows one in a `PreviewSurface` (`app/(studio)/_components/preview/`), with its controls before the frame. Compare two frames shows two, side by side, each with its own grant, nonce, port, and appearance override (`appearance-controls.tsx`), a composition, design language, color scheme, and typography the frame's next grant renders in place of the site's. Linking their scrolling and navigation is off until the owner turns it on: then `frame-link.ts` passes one frame's `navigated` and `scrolled` to the other as `navigate` and `scroll-to`, each loaded under that frame's own grant. `grant-session.ts` mints the frame's grant, renews it on a heartbeat, asks its status when a renewal fails or a load brings no hello within 2 seconds, mints again when it's superseded, expired, or unknown but never after `preview_blocked`, and revokes it as the frame goes, or as the page does, with a `keepalive` request on `pagehide`. The surface opens Studio's half of the channel to the frame, sends it the environment and its lifecycle (`frame-lifecycle.ts`), refreshes it at most once every 2 seconds (`refresh-throttle.ts`), shows a link it cancelled only as text with an Open button, and on a logout, a 401, or `session_ended`, here or on the `studio-session` channel from another tab, sends the frame to `about:blank`, and for a grant's `session_ended` posts that `logout` to the other tabs itself, as `studioFetch` does for a 401. `lib/preview-frame.ts` decides the frame's sandbox, `allow-scripts` alone, and `allow-same-origin` too only for `owner` frames on `PORTFOLIO_PREVIEW_ORIGIN`, where `src/proxy.ts` serves the preview's paths alone. `lib/environment.ts`'s `environmentAttributes(selection, override)` turns the site's selection and a grant's environment into the boundary's `data-display-mode`, `data-contrast`, `data-motion`, and `data-enhancement`, and both the grant's render and the agent's `environment` handler call it, so motion only ever reduces. `packages/preview-fixtures` holds `fixture-environment`, which the fixture gate admits only with `PREVIEW_FIXTURES=1`. It dispatches each `lifecycle` Studio sends on `window` as a `kgn-preview-lifecycle` event, the last one kept at `window[Symbol.for('kgn-preview.lifecycle')]`, for #6's runtime to pause on. ## Storage

Under `read-only` the documents in `PORTFOLIO_SOURCE_DIR` are the portfolio, read once at startup. Under `owner` they're import input, and what visitors see is a revision in the store in `PORTFOLIO_DATA_DIR` (#3), which `@portfolio/core` holds:

- **Revisions**: each one written once and never changed, under `revisions/<revisionId>/`: the documents as written, their normalized models, the snapshots derived at publish, and a manifest. A document's `contentHash` covers #4's canonical form of its model, so YAML and JSON with equal content hash equally, its `sourceHash` covers its bytes, and the `unitHash` covers every document and snapshot. The manifest records them with the parent revision, the author, and what rendered it, never a secret or a deployment setting.
- **The pointer**: `publication/live.json` names the live revision. Renaming a new one over it is the commit point of every publish, import, rollback, and recover, so a crash leaves the old revision live or the new one. The `PublicationService` is the only code that moves it, under the publication lock, and each move appends an event to `publication/events/`.
- **Drafts**: one working draft, saved with its findings whether or not it validates. Only a publish needs a valid unit.
- **Blobs**: under `assets/sha256/`, by the SHA-256 of their bytes, for #10's media.
- **First start**: visitors are served through `RevisionCatalogReader`, which serves nothing, a 503, while the store is empty. Owner's `documents.shape` startup requirement, after the repair, imports the mounted pair into an empty store as revision 1, as `operator`, checked as a publish, as `portfolio-store import` is. Once a revision exists, the mounted pair is import input, and its findings only warn.
- **`portfolio-store`**: the operator's command line, `runCli` in `packages/core/src/cli.ts`, with its entry `apps/web/scripts/portfolio-store.ts` binding the build's registry and #4's pair loader. The image ships it bundled as `/app/bin/portfolio-store.mjs`. It imports, rolls back, recovers, backs up and restores, keeps retention, and verifies, beside the server and under the same lock.

Every file operation goes through an `FsPort` that names a crash point at each write, sync, and rename, and the crash tests stop the store at each one, in the test process and by killing a child process. [deployment.md](deployment.md#the-revision-store) covers running it.

## Theme resolution

Every page renders inside one document boundary, which `lib/document-appearance.ts` resolves with `resolveAppearance()`: the site's selection, the visitor's preference on the axes `visitorControls` makes selectable, from the `portfolio_appearance` cookie under owner and read-only and from the query under demo, and a preview's environment, which reads no visitor value. The boundary's attributes say the variant, the three packs, the display mode, contrast, motion, and enhancement, and it links the platform stylesheet and the selected packs' alone, so the first paint is the page's appearance and no script changes it. A page with no site to read, the 503 and the error page, renders the platform's fallback packs. The visitor control, in each variant's `VisitorControlSlot`, posts to `POST /api/appearance`, which sets the cookie from the canonical origin only; the page then renders again in the new selection. No variant renders a theme toggle.

## Drift gates

These scripts enforce parity:

- **`skills/scripts/sync-checks.mjs`** checks that `section-kinds.md` matches `CORE_SECTION_KINDS`, that `kit-catalog.md` mentions every kit export, that `schema.md` mentions every section kind, and that both SKILL.md frontmatters parse and stay under their length caps.
- **`skills/portfolio-author/scripts/validate.mjs`** validates a directory's `portfolio.yml` and `site.yml` the way the server does at startup, and prints each problem with its file, line, column, code, and how to fix it.
- **`pnpm check:variants`** generates the registry and lints every registered variant's source and styles, the kit modules they reach for the clock and randomness rules, and the kit's shared stylesheet for appearance. It's a lint over code the host trusts at build time, not a sandbox. CI runs it in its own `check-variants` job; `pnpm check:registry` checks that two registry builds match, the experience segments and the compiled files included, under each fixture flag's values, `APPEARANCE_FIXTURES=1`, `PREVIEW_FIXTURES=1`, `QUALITY_FIXTURES=1` and `meta`, and `BUDGET_FIXTURES=1` and `over`, and with none.
- **`pnpm check:appearance`** reads the registry and runs #19's contrast gate over every registered combination of design language, color scheme, typography, and display mode, with the hierarchy check and the layer order of every layered stylesheet. It also registers each known-bad input in `packages/appearance/test/fixtures/` in turn and fails unless the gate fails on each for the reason it names; `--fixture <name>` runs the gate with one of them, such as `bad-contrast`. Its targets come from `quality/thresholds.json` (#11), and it gates #11's tier fixture packs, which `QUALITY_FIXTURES` admits, as shipping packs. CI runs it in the `static` job.
- **`pnpm quality:meta`** (#11) runs each quality gate on its known-bad and known-good inputs and fails unless every known-bad one fails for the reason it names and every known-good one passes.
- **`pnpm test:variants`** renders every registered composition on every contract fixture (`packages/variant-contract/fixtures/`) and on the bundled sample, in six modes, with the hidden canary and render parity, against the production build. CI's `variants` job compares the platform's own variants' screenshots in the pinned Playwright image.
- **`pnpm test:external-variant`** packs the reference third-party variant in `tests/external-variant/`, installs the tarball in a temporary `git worktree`, runs the variant specs and its own checks, and removes it, with `git status` showing no host edit after the add and nothing after the remove.

Run them with `pnpm check:skills`, `pnpm check:variants`, `pnpm check:appearance`, `pnpm test:variants`, `pnpm test:external-variant`, and the per-script test suites listed in [CONTRIBUTING.md](../CONTRIBUTING.md#checks). [docs/variants.md](variants.md#testing-a-variant) has the details.

## Skills

Two AI-agent skills under `skills/`:

- **`portfolio-author`** guides an agent to build the portfolio and site documents from any source (a resume PDF, a LinkedIn export, a GitHub username, a conversation). The agent loads references on demand: the schema, curation principles, quality rules, the section-kinds catalog, and examples.
- **`variant-developer`** guides an agent to build a new composition from concept to ship. It walks through DESIGN.md, the manifest, renderers, layout CSS, and `pnpm check:variants`, with a visual companion (an HTTP server and file watcher in mockup mode, the dev server on the bundled sample in preview mode), and `pnpm test:variants` for screenshots in every mode.

Both skills enforce drift parity through the gates above. See [skills/](../skills/) for the SKILL.md files and references.

## Why this shape

- **Documents, not code.** Content authors don't touch code, and code authors don't touch content.
- **Content apart from presentation apart from deployment.** The portfolio document is portable between sites, the site document is how one site presents it, and the environment is one deployment's settings and secrets. A presentation change never edits content, and neither document can carry a secret.
- **Profession-neutral sections plus extensions.** The core kinds don't assume a profession, and a profession package adds its own fields and kinds under its namespace without weakening the core checks.
- **One clean break.** The old one-file format has no compatibility reader. `pnpm config:migrate` converts it once, and startup refuses it.
- **Variants are packages, not configs.** That encourages real diversity of composition and lets variants pull in heavy dependencies (Three.js, R3F) without burdening the rest. Installing one is a dependency, and nothing else.
- **Composition apart from appearance.** A variant arranges; the appearance system (#19) colors, sets type, and shapes. An owner can pair any composition with any appearance.
- **Kit, not framework.** Variants opt into the utilities they need. The kit grows when patterns repeat across variants, not preemptively.
- **Drift gates over conventions.** Automated checks beat documentation as instructions for keeping the schema, the references, and the skills aligned.
